# Настройка текущего хранилища QA Report Corporate

Инструкция для системного администратора. Выполняйте команды в каталоге рабочего
Compose проекта QA Report Corporate. При обновлении сохраняйте его имя и тома.

## 1. Указать адрес S3 API и существующий бакет

Текущие значения в корпоративной конфигурации:

```dotenv
QA_STORAGE_ENDPOINT=https://minio-buckets.adv.ru
QA_STORAGE_BUCKET=qa-tools
QA_STORAGE_REGION=us-east-1
QA_STORAGE_ACCESS_KEY_FILE_HOST=./secrets/storage_access_key
QA_STORAGE_SECRET_KEY_FILE_HOST=./secrets/storage_secret_key
```

Укажите их в рабочем `.env`. Если установка уже использует другие значения,
сначала сверяйте их с действующей конфигурацией и администратором MinIO.
`QA_STORAGE_ENDPOINT` - HTTPS-адрес **S3 API**, без имени бакета, пути и адреса
веб-консоли MinIO. Бакет задаётся отдельно. Регион должен совпадать с настройкой
MinIO; `us-east-1` - текущее значение по умолчанию.

Используйте прежний бакет и ключи с доступом к прежним объектам. Смена адреса или
бакета не переносит данные: записи существующих вложений продолжают ссылаться
на прежние ключи объектов. Облако, публикации и ручные загрузки используют один
настроенный бакет с разными префиксами.

## 2. Подключить ключи через файлы

В каждом файле должна быть одна строка: в `storage_access_key` - access key,
в `storage_secret_key` - secret key. Обычный завершающий перенос строки допустим.
Если файлы уже существуют, сохраните их содержимое. Для первоначального
заполнения используйте защищённый редактор или менеджер секретов; не передавайте
ключи аргументами команд, в чате или в Git.

Контейнер работает от `node` с UID/GID `1000:1000`. Для файлов из примера:

```bash
sudo chown 1000:1000 ./secrets/storage_access_key ./secrets/storage_secret_key
sudo chmod 600 ./secrets/storage_access_key ./secrets/storage_secret_key
```

В Compose файлы подключаются как secrets. Имена переменных отличаются:

| Где | Access key | Secret key |
| --- | --- | --- |
| `.env` на хосте, путь к исходному файлу | `QA_STORAGE_ACCESS_KEY_FILE_HOST` | `QA_STORAGE_SECRET_KEY_FILE_HOST` |
| Внутри контейнера, задаёт `compose.yaml` | `QA_STORAGE_ACCESS_KEY_FILE=/run/secrets/storage_access_key` | `QA_STORAGE_SECRET_KEY_FILE=/run/secrets/storage_secret_key` |
| Запуск Node без Docker | `QA_STORAGE_ACCESS_KEY_FILE` с путём на этом сервере | `QA_STORAGE_SECRET_KEY_FILE` с путём на этом сервере |

При запуске без Docker переменные `_FILE_HOST` не читаются приложением: задайте
обычные `_FILE`. Если задан `_FILE`, он имеет приоритет над значением ключа
в переменной окружения. Недоступный файл нужно исправить, а не обходить другим ключом.

## 3. Проверить права и сеть

Сервисной учётной записи MinIO нужны `s3:GetObject`, `s3:PutObject` и
`s3:DeleteObject` в бакете `qa-tools` для префиксов:

- `reports/*` - ручные загрузки;
- `shared-reports/*` - опубликованные отчёты и ответы разработчиков;
- `cloud-reports/*` - личные облачные копии;
- `healthchecks/*` - временные объекты диагностической команды.

Проверка существования объекта тоже выполняется через GET; перечисление
бакетов, создание бакета и изменение политик приложению не нужны. Бакет должен
быть приватным. Доступ браузера к MinIO и правила CORS для него не требуются:
вложения проходят через корпоративный сервер QA Report.

Из контейнера должны работать DNS, HTTPS и проверка сертификата endpoint.
Если MinIO использует внутренний CA, передайте PEM-цепочку дополнительным
read-only mount и задайте контейнеру `NODE_EXTRA_CA_CERTS` с путём к ней.
CA для LDAPS настраивается отдельно. Не отключайте проверку TLS.

## 4. Обновить приложение и проверить подключение

Перед обновлением сохраните резервные копии базы отчётов, тома `admin_config`
и бакета. База содержит метаданные, ответы, профили и разрешения; одного бакета
для восстановления недостаточно. Сохраните также существующие secrets.

```bash
docker compose build qa-report
docker compose up -d --no-deps qa-report
docker compose ps
curl --fail http://127.0.0.1:4173/api/health
docker compose exec -T qa-report npm run storage:check
docker compose exec -T qa-report npm run storage:check -- --roundtrip
```

Последняя команда создаёт случайный объект `healthchecks/<uuid>`, читает его,
сверяет содержимое и удаляет. Она не читает отчёты и не изменяет настройки бакета.
Без `--roundtrip` проверяется только формат конфигурации. Проверка использует
тот же код настройки S3, что и облако с публикациями. Ключи в вывод не попадают.
При ошибке удаления команда укажет точный временный объект для ручной очистки.

`objectStorageConfigured: true` в healthcheck означает наличие настроек,
а не успешное соединение с MinIO. Сеть и права подтверждает `--roundtrip`.

Не выполняйте `docker compose down -v` при обновлении. Если рабочий Compose
хранится отдельно от репозитория, перенесите нужные настройки точечно, сохранив
подключения существующих томов `reports_data` и `admin_config`.

## 5. Включить возможности в админке

Если отдельный администратор ещё не настроен:

```bash
docker compose build admin-setup
docker compose run --rm --no-deps admin-setup
docker compose up -d --no-deps --force-recreate qa-report
```

Откройте `/owner/` на HTTPS-адресе QA Report или ранее настроенный адрес админки.
Вход администратора отдельный: корпоративный пароль AD сюда не подходит.
В разделе «Публикация и хранилище S3» доступны:

- «Разрешить публикацию и обновление по ссылке»;
- «Разрешить загрузку новых вложений в S3»;
- «Разрешить сохранение личных отчётов в облаке».

Для новой установки публикация и новые вложения разрешены после настройки S3,
личное облако изначально выключено. Существующие сохранённые настройки
не сбрасываются. Общий запрет сильнее индивидуального разрешения.
Запрет облачного сохранения сохраняет чтение и удаление прежних копий;
запрет новых вложений сохраняет чтение прежних файлов и текстовые изменения.

В разделе «Пользователи» появляются сотрудники после подтверждённого входа или
обращения с действующей корпоративной сессией. Можно отдельно запретить
публикацию, новые вложения и облачное сохранение. Это каталог пользователей
QA Report, а не полный список AD. Изменение этих разрешений не выдаёт прав
администратора и не меняет права в Jira или AD.

## 6. Проверить результат двумя сотрудниками

1. Войти через AD, открыть «Профиль», сохранить имя и аватар. После повторного
   входа они должны сохраниться; email остаётся корпоративным.
2. Сохранить отчёт с вложением в личное облако. В том же аккаунте в другом
   браузере открыть копию и скачать вложение. Другой сотрудник не должен
   получить доступ по личной облачной ссылке.
3. Опубликовать отчёт для разработчика. Второй сотрудник проходит корпоративный
   вход, открывает ссылку, сохраняет ответ и прикрепляет файл.
4. Запретить одному сотруднику новые вложения: его новая загрузка должна
   отклоняться, прежние файлы должны открываться.
5. Вернуть разрешение, затем проверить общий запрет: индивидуальное разрешение
   не должно его обходить. После проверки восстановить рабочие настройки.

## Если проверка не прошла

| Результат | Что проверить |
| --- | --- |
| Не читается файл ключа | `_FILE_HOST` на хосте, secret mount, `_FILE` внутри контейнера и доступ UID 1000 |
| Запрос к S3 не выполнен | DNS, сеть контейнера, HTTPS endpoint, цепочку CA и время сервера |
| S3 вернул 403 | Пару ключей, регион, подпись и права на нужный префикс |
| S3 вернул 404 | Существование бакета; для прежнего вложения - сохранность объекта в прежнем бакете |
| Диагностика прошла, но запись отчёта запрещена | Общие и индивидуальные разрешения в админке |

При ротации ключей не меняйте endpoint, бакет и префиксы объектов. Новая
сервисная учётная запись должна иметь доступ и к уже сохранённым объектам.
После изменения Compose или `.env` пересоздайте сервис командой `up -d`;
один `docker compose restart` не применяет новые переменные окружения.

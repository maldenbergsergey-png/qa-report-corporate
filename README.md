# QA Report Corporate

QA Report Corporate — корпоративная версия редактора QA-чек-листов,
предназначенная для использования в корпоративном контуре с ограниченным и
безопасным набором возможностей.

QA Report — web-инструмент для создания, ведения и публикации QA-чек-листов.
Он помогает быстро собрать проверочный отчёт, импортировать таблицы из Jira,
добавить фактические результаты, скриншоты, файлы и код, а затем отправить
готовый отчёт обратно в Jira или сохранить его в истории.

Docker-сборка включает все ресурсы установки PWA, в том числе Worker для
чтения метаданных. `tests/pwa.test.js` проверяет не только скрипты HTML,
но и весь набор ресурсов из `sw.js`: отсутствие файла блокирует установку
обновления, сохраняя прежнюю рабочую сборку. Кнопка обновления повторно
проверяет ожидающий Worker после завершения его установки.
Индикатор «Что нового» учитывает содержимое записи: дополнения за ту же
дату снова отображаются как непрочитанные без смены номера версии.

Проверка обновления: `node tests/pwa-update.browser.cjs` воспроизводит
отсутствующий ресурс, повторную установку и сохранение текста перед активацией.
Диагностика отрисовки: `node tests/editor-rendering-performance.browser.cjs`
сравнивает ввод и Backspace в ячейке без вложений при 1500 и 40 строках в DOM.
Автосохранение в этом эксперименте выключено, CPU замедлен в четыре раза;
в модели остаются все строки. Это проверка влияния размера DOM, а не готовая
виртуализация. Для обоих сценариев нужен Playwright.

При наборе текста редактор обновляет изменённое поле; сводка пересчитывается
при изменении заполненности строки. Автосохранение и история отмены используют
обновлённую модель без повторного обхода всей таблицы. Полная сверка с редактором
сохраняется перед явным сохранением, закрытием страницы и структурными операциями.

Копии контейнеров отчёта переиспользуют неизменяемые строки вложений. Сохранение
и история отмены используют одно представление содержимого; счётчик локальных
правок не позволяет завершившемуся старому сохранению изменить статус новых
правок. Записи автосохранения выполняются в порядке их запуска.

История отмены и повтора ограничена суммарно 100 шагами и оценкой памяти
32 МиБ, включая текущий снимок (два байта на символ JSON). Старые шаги
удаляются первыми; ближайшая отмена и ближайший повтор сохраняются даже тогда,
когда каждый полный снимок сам превышает бюджет. Поэтому это ограничение
глубины истории, а не жёсткий предел памяти всего редактора. Вложения в
оставшихся шагах сохраняются полностью; формат отчёта и IndexedDB не изменён.
При обновлении истории освобождается кеш сохранённого содержимого,
если он относится к другому отчёту или поколению правок.
`tests/editor-memory.browser.cjs` проверяет 24 отдельных изменения в отчёте
с 500 строками, восемью PNG и текстовым файлом, затем отмену, повтор, запись
IndexedDB и открытие после перезагрузки. `QA_REPORT_INPUT_BASELINE` задаёт
предыдущий `app.js` для сравнения; `QA_REPORT_MEMORY_RESULTS` сохраняет замер JSON.

Замер 07.10.2026 в локальном headless Chromium на этом сценарии:
после 24 правок JSHeapUsedSize публичной версии снизился с 791 до 66 МиБ,
корпоративной — с 791 до 66 МиБ. Это память JavaScript после сборки мусора,
без памяти декодированных изображений и GPU; замер не устанавливает причину
конкретного падения Chrome на другом устройстве.

Крупные отчёты сохраняются в прежнюю IndexedDB. При обычном автосохранении
копия содержимого больше 1 048 576 символов не записывается в localStorage; перед
закрытием страницы прежняя синхронная резервная запись всё равно выполняется,
если позволяет квота браузера. Статус «Сохранено» для крупного отчёта появляется
после завершения записи IndexedDB. Старый полный черновик не заменяется указателем:
отдельный небольшой ключ запоминает последний успешно записанный отчёт для
открытия с главного адреса. Между окнами передаются метаданные сохранения,
а содержимое читается из хранилища. Сообщения старых вкладок продолжают приниматься.

Проверка свежести и сохранение читают метаданные истории в отдельном Worker,
чтобы большие документы не разбирались в потоке интерфейса. При недоступном
Worker используется прежний путь чтения. Обслуживание истории читает только
даты и идентификаторы после превышения лимита 50 записей.

Корпоративная очистка HTML сохраняет прежние правила: загрузка новых объектов
и изменение поля проходят полный sanitizer. Только неизменившееся значение,
ранее полученное от sanitizer, использует результат предыдущей проверки;
кеш привязан к объекту поля через WeakMap и не отключает проверку импортов.

Форматы черновиков, IndexedDB (версия 1) и файлов `.report` не изменены;
миграция или удаление старых чек-листов не выполняются. Идентификаторы, вложения,
номера пунктов, статусы и дополнительные поля сохраняются. Браузерные проверки
`tests/editor-compatibility.browser.cjs` проверяют старый полный черновик,
открытие существующих записей IndexedDB без нового ключа, вложения, отмену,
повторное открытие и обмен между окнами на изолированных синтетических данных.
Замер `tests/editor-typing-performance.browser.cjs` использует 500 строк и
10 реальных PNG: непрерывный ввод, ввод с паузами и редактирование ячейки
с изображением. `QA_REPORT_INPUT_BASELINE` позволяет сравнить сохранённую
предыдущую сборку на том же сценарии; `QA_REPORT_INPUT_RESULTS` сохраняет JSON.
Для запуска браузерных проверок нужен Playwright; `QA_REPORT_PLAYWRIGHT`
может указывать на уже установленный модуль.

Замер 01.10.2026 в локальном headless Chromium на синтетическом отчёте
(500 строк, 10 PNG, около 31,3 МБ; 13 символов с паузой 650 мс):
основной поток браузера занял 10.44 → 1.01 с,
снижение 90%. Среднее время обработчика ввода в ячейке
с изображением — 34.4 → 18.8 мс; максимальная длинная задача
в четырёх сценариях — 416 → 55 мс. Это замер сценария,
а не обещание такой же скорости на любом устройстве. Для сравнения использована
предыдущая сборка `fde5fa9`; автосохранение и история отмены были включены.

Вставка вложений из буфера и выбор файлов выполняются без ожидания сети.
Лимиты обновляются в фоне и временно запоминаются отдельно для текущего отчёта
и Jira; неизвестный лимит Jira не мешает локальной вставке. Перед публикацией
актуальные ограничения проверяются повторно.

README описывает текущее состояние проекта. Если меняется сценарий, API,
настройка, ограничение или способ запуска, этот файл нужно обновлять в том же
изменении.

Пошаговая инструкция для владельца продукта, AD/Jira-администраторов и DevOps находится в [DEPLOYMENT.md](DEPLOYMENT.md).

## Корпоративная аутентификация

Вход в QA Report выполняется через AD. Jira использует отдельную делегированную OAuth 1.0a авторизацию, потому что
общая LDAP-учётная база сама по себе не передаёт серверу Jira-сессию пользователя.

```text
Browser → HTTPS reverse proxy → QA Report Web/BFF
                                ├→ LDAPS → Active Directory
                                ├→ signed 8-hour HttpOnly session
                                ├→ SQLite/MinIO scoped by session email
                                ├→ Jira 7.3.2 OAuth 1.0a → user identity
                                └→ Jira 8.11.1 OAuth 1.0a → user identity
```

QA Report остаётся монолитным Node.js Web/BFF: UI и доверенный API работают в одном процессе. Поэтому отдельный
internal JWT между BFF и backend не нужен — подтверждённый email передаётся внутри процесса в `request.user`,
а не через сетевой заголовок. Порт приложения публикуется только на loopback для внешнего HTTPS proxy.

Поток входа:

1. Любая защищённая страница без сессии перенаправляет на `/login?callbackUrl=...`; API возвращает JSON `401`.
2. Форма получает same-origin CSRF token и отправляет email/password на `/api/auth/login`.
3. Сервер нормализует email, проверяет лимиты по email и реальному IP, затем выполняет service bind, безопасный LDAP search и отдельный user bind по UPN.
4. Только успешный user bind создаёт подписанную 8-часовую cookie (`HttpOnly`, `SameSite=Lax`, `Secure` в production, `Path=/`). Пароль очищается и не входит в token, БД или логи.
5. Все защищённые пользовательские API извлекают владельца только из проверенной сессии. `X-User-Email`, workspace key и browser ID не являются источником identity.
6. Единый frontend handler переводит на login при `401`, сохраняя локальный pathname/query. Logout защищён CSRF и удаляет cookie.

### LDAPS

Разрешён только `ldaps://`, TLS 1.2+, проверка цепочки CA и имени `LDAP_TLS_SERVERNAME`. Файл CA монтируется как
secret/read-only file, а `LDAP_CA_SHA256` фиксирует ожидаемый fingerprint. Отключение TLS verification и plaintext
fallback отсутствуют. Ослабление OpenSSL `@SECLEVEL=0` намеренно не добавлено: если старый DC всё ещё требует его,
предпочтительное инфраструктурное исправление — перевыпустить сертификат DC на SHA-256/RSA-2048+.

Для локальной разработки можно задать `NODE_ENV=development`, `DEV_LOGIN_EMAIL` и `DEV_LOGIN_PASSWORD`.
Этот аккаунт принимается только при запуске сервера на loopback (`127.0.0.1`, `::1` или `localhost`) и всегда
отключён в production. Для остальных email приложение продолжает использовать LDAPS.

### Jira permissions

Обе Jira Data Center подключаются как отдельные OAuth 1.0a Application Links. Пользователь один раз подтверждает
доступ в каждой Jira, после чего access token хранится на сервере в AES-256-GCM зашифрованном виде и привязывается
к email корпоративной сессии. Комментарии и вложения выполняются с реальными permissions Jira-пользователя.
При отсутствии или отзыве token операция останавливается; fallback на service account отсутствует. AD-пароль в Jira
не передаётся. По умолчанию email из Jira `/myself` обязан совпадать с email AD-сессии.

## Обязательная конфигурация

Несекретные env: `QA_REPORT_PUBLIC_URL`, `QA_REPORT_TRUST_PROXY`, `LDAP_URL`, `LDAP_BIND_DN`,
`LDAP_SEARCH_BASE`, `LDAP_TLS_SERVERNAME`, `LDAP_CA_SHA256`, login rate limits, `JIRA_INSTANCES_JSON`, `JIRA_OAUTH_CONSUMER_KEY`,
`QA_JIRA_ALLOWED_ORIGINS` и параметры object storage.

Secrets/files: `AUTH_SECRET_FILE` (не менее 32 случайных байт), `LDAP_BIND_PASSWORD_FILE`, `LDAP_CA_FILE_HOST`,
`JIRA_OAUTH_PRIVATE_KEY_FILE`, `JIRA_TOKEN_ENCRYPTION_KEY_FILE` и storage credentials. Примеры путей находятся в
`.env.example`; содержимое `secrets/` исключено из Git. При ротации auth secret существующие сессии становятся
недействительными.

Reverse proxy должен использовать конфигурацию из `deploy/`: allowlist host через `server_name`, самостоятельно
формировать forwarded headers, очищать identity/Authorization headers, ограничивать login endpoint и upload,
отключать buffering и иметь read timeout не меньше backend timeout.

> Важно: отключённая в AD учётная запись сохраняет уже выданную stateless-сессию максимум до 8 часов. Более строгое
> немедленное отзывательство потребует server-side session registry/token version или сокращения срока сессии.

## Назначение версии

- Эта версия отделена от личной версии QA Report и развивается как самостоятельная корпоративная сборка.
- Функциональность может быть урезана в соответствии с требованиями безопасности корпоративного контура.
- Запрещено автоматически возвращать функциональность, предназначенную только для личной версии (`personal-only`).
- Внешние интеграции, хранение токенов, облачные возможности и любые сетевые взаимодействия можно добавлять только после отдельного согласования.

## Корпоративные ограничения

- Не хранить в репозитории секреты, токены, пароли и cookie.
- Не добавлять внешние облачные интеграции без явного запроса и согласования.
- Не восстанавливать функциональность личной версии, если она была удалена из корпоративной.
- Опасный backend-функционал должен быть удалён либо защищён серверными проверками; скрытия только на уровне UI недостаточно.
- Любые изменения, влияющие на безопасность, должны быть явно описаны в MR.

## Разрешённый функционал

Базово в корпоративной версии допускаются:

- редактор чек-листов;

- локальное хранение;
- интеграции, отдельно разрешённые для корпоративного использования;
- безопасная история отчётов, если она включена в корпоративной версии.

Описанные ниже возможности не считаются автоматически разрешёнными: их
доступность определяется конфигурацией и требованиями безопасности конкретного
корпоративного контура.

## Связь с личной версией

- Личная версия QA Report находится в отдельном репозитории.
- Общие исправления можно переносить вручную через `cherry-pick`.
- Перед переносом необходимо проверить, не возвращает ли исправление удалённый или запрещённый функционал.
- Изменения корпоративной версии должны оставаться изолированными от `personal-only` доработок.

## Правила для Codex

- Работать с проектом как с корпоративной версией QA Report.
- Не возвращать удалённый функционал из личной версии.
- Не добавлять внешние интеграции без явного запроса и согласования.
- При переносе общего исправления адаптировать его под корпоративные ограничения.
- Не изменять `.env`, секреты, runtime-данные и локальные базы.
- После правок указывать изменённые файлы и выполненные проверки.

## Пользовательские Возможности

### Окно настроек

Настройки открываются поверх редактора в окне фиксированного размера. Меню
слева сгруппировано по задачам: «Чек-лист», «Данные», «Интеграции» и
«Приложение». Внутри прокручивается содержимое выбранной страницы; заголовок
и нижняя кнопка «Сохранить» остаются видимыми. При переходе между страницами
прокрутка возвращается в начало. Светлая, графитовая и тёмная темы используют
те же цвета и элементы управления, что и основной редактор.

«Нумерация» относится к текущему чек-листу. «Столбцы» объединяют набор для
новых чек-листов и разделов с закреплением номера и статуса для всех чек-листов
этого браузера. «Синхронизация» содержит прежние настройки облачного хранения
и ключа пространства. Сохранение выполняется прежней общей кнопкой, а тема
применяется сразу. Закрытие без сохранения не применяет изменения в полях.

В корпоративной сборке Jira подключается от корпоративной учётной записи.
Connect используется для диктовки и подготовки черновиков багов с ИИ.
Интеграция EVA и настройки дисков в эту сборку не добавляются.


### Редактор чек-листов

- Несколько разделов в одном отчёте.
- Добавление, удаление, дублирование и перемещение строк.
- Создание нового раздела из выбранной строки.
- Пользовательские колонки в каждом разделе.
- Переименование, перемещение и изменение ширины колонок.
- Стабильные `sectionId`, `rowId`, `columnId` для сохранения и сравнения версий.
- Служебные колонки с номером строки и статусом.
- Автоматическая сводка по статусам.

### Статусы проверок

Поддерживаются:

- `OK`
- `НЕ ОК`
- `ПОЧТИ ОК`
- `НЕ ПРОВЕРЕНО`
- `ЧАСТИЧНО ПРОВЕРЕНО`
- `ТРЕБУЕТ УТОЧНЕНИЯ`

Сводка пересчитывается автоматически. Пустые строки не учитываются в итоговой статистике.

### Текст, код, изображения и файлы

- Форматированный вводный текст.
- Жирный, курсив, подчёркивание, зачёркивание, списки, ссылки и цвет текста.
- Нажатие на ссылку в ячейке или вводном тексте открывает компактное окно с адресом и названием. Иконки внизу позволяют открыть ссылку в новой вкладке, показать полный адрес вместо подписи и применить изменения; у каждой есть подсказка. Кнопка ссылки на панели и Ctrl/⌘+K открывают то же окно для текущего выделения или позиции курсора.
- В режиме выделения строк ссылки открывают то же окно с кнопкой «Открыть в новой вкладке». Переход сохраняет выделенные пункты и содержимое отчёта.
- Переход выполняется только кнопкой открытия. Выделение, перетаскивание текста, копирование, двойной щелчок и нажатие на ссылку со служебными клавишами не запускают переход. Кнопка «Показать полный адрес» заменяет подпись адресом, сохраняя ссылку. Тот же результат даёт сохранение с пустым полем «Текст ссылки (необязательно)»; изменение можно отменить. Для открытия и сохранения допустимы только корректные адреса HTTP/HTTPS, `www.` дополняется до HTTPS.
- Кодовые блоки в ячейках и вводном тексте.
- Полноэкранное редактирование кода.
- Копирование кода с Jira-обёрткой `{code}...{code}`.
- Вставка изображений из файлов и буфера обмена.
- Просмотр изображений в увеличенном виде.
- Перетаскивание изображений и кодовых блоков между ячейками.
- Вставка файлов-карточек.
- Нажатие на карточку файла или «Просмотреть файл» в меню «Ещё действия» открывает текстовое вложение до 2 МБ: XML, JSON, TXT, логи, CSV, YAML и исходный код. Можно выбрать кодировку, включить перенос строк, скопировать текст или скачать исходный файл. Enter и пробел открывают просмотр с клавиатуры; Esc закрывает окно.
- «Читаемый текст» включён автоматически: последовательности `\uXXXX` в JSON и других текстовых файлах показываются обычными буквами. Снимите флажок, чтобы увидеть исходный текст. «Копировать текст» копирует выбранный вид, «Скачать файл» сохраняет оригинал. Корректный JSON автоматически показывается с переносами и отступами в два пробела по структуре объектов и массивов. Числа, порядок и повторяющиеся ключи, буквальные обратные слеши и управляющие символы сохраняются. Некорректный JSON, слишком глубокие структуры и слишком большой результат форматирования показываются с исходными отступами.
- Просмотр читает только локальные данные вложения и не меняет файл или отчёт. XML и HTML показываются как текст без выполнения разметки. Для ссылок «В Jira» сначала выберите «Скачать в браузер»; файлы из хранилища, двоичные и неподдерживаемые форматы открываются после скачивания на устройстве.

### История и версии

- Автосохранение текущего чек-листа.
- Полное локальное хранение в браузере по умолчанию.
- Опциональная серверная история в SQLite, включается во вкладке "Настройки → Данные → Синхронизация".
- Необязательный ключ пространства позволяет открыть одну серверную историю в разных браузерах внутри одной корпоративной учётной записи; без ключа используется личное пространство пользователя.
- Короткий публичный ID экземпляра, например `851a9bd2`.
- URL текущего чек-листа: `/report/<publicId>`.
- Модалка истории с поиском, источником версии, public ID и комментарием.
- Окно истории открывается сразу: до загрузки записей видны карточки-заглушки и подпись «Загружаем историю…». Поиск учитывает текст, введённый во время ожидания. На узком экране поиск и кнопки переносятся, записи прокручиваются внутри окна.
- Отдельный пользовательский комментарий для каждого экземпляра отчёта.
- Удаление локальных и серверных записей из истории.

Браузерная проверка загрузки истории: `node tests/history-loading.browser.cjs`
с Playwright (или путём в `QA_REPORT_PLAYWRIGHT`). Проверяются задержка сохранения
и чтения, поиск во время ожидания, повторное открытие, пустой список, повтор после
сбоя, темы и уменьшенная анимация. Используются тестовые данные и временная база.

### Конфликты версий

- Обнаружение отличий между локальной и облачной версией.
- Облачные конфликты и синхронизация работают только если включён флаг "Сохранять чек-листы в облачном хранилище".
- Сравнение по содержимому, а не по служебным полям вроде `updatedAt` или `revision`.
- Diff по стабильным ID разделов, строк и колонок.
- Подсветка новых строк, колонок, разделов и изменённых ячеек.
- Защита от перезаписи пользовательских названий колонок дефолтным или пустым значением.
- Выбор облачной версии.
- Явная перезапись облака локальной версией.
- Сохранение обеих версий: облачная остаётся на старом `publicId`, локальная расходящаяся версия создаётся как новая копия с новым `publicId`.

## Основные Сценарии

### Создать чек-лист

1. Откройте приложение.
2. Заполните ссылку на Jira-задачу, окружение и итоговый статус.
3. Добавьте разделы, строки и колонки.
4. Заполните проверки, ожидаемый и фактический результат.
5. При необходимости добавьте изображения, файлы или код.
6. Скопируйте отчёт, экспортируйте XLSX или отправьте результат в Jira.

Новый чек-лист получает случайный короткий `publicId` и URL вида:

```text
/report/851a9bd2
```

### Открыть конкретный чек-лист

Перейдите по URL:

```text
https://qa-report.company.ru/report/851a9bd2
```

Если ID найден в локальном кэше или, при включённом облаке, в серверной истории текущего пространства,
приложение откроет нужный чек-лист. Если ID неизвестен, будет показано понятное
сообщение с возможностью создать новый чек-лист.

Старый формат `/#/checklists/<id>` поддерживается как fallback.

### Проекты в истории

Список слева от поиска позволяет показать «Все проекты», один проект или
«Без проекта». Фильтр работает вместе с поиском по задаче, названию и комментарию;
поиск также учитывает заданное название проекта. Рядом с ключом задачи показана
метка проекта. Если задано название, в выпадающем списке показано только оно,
без ключа. Счётчик при фильтрации показывает количество найденных записей.

Проект определяется по префиксу ключа задачи: `SHOP-123` относится к `SHOP`.
Это работает и для ранее сохранённых локальных и облачных чек-листов без
повторного сохранения. Записи без распознаваемого ключа относятся к «Без проекта».

В «Настройки → Данные → Проекты» ключи из истории и текущего чек-листа показаны
без повторов. Пока список загружается, отображаются заглушки строк. Задайте
название на любом языке и цвет метки через палитру или HEX-код (`#E5484D`,
`#F00` или `E5484D`), затем нажмите «Сохранить». Неверный код не сохраняется.
Пустое название возвращает исходный ключ; крестик возле цвета возвращает
стандартный цвет. Закрытие без сохранения оставляет прежние названия и цвета.
Названия хранятся в `qa-report-project-names-v1`, цвета — в
`qa-report-project-colors-v1` в localStorage текущего браузера,
отдельно от отчётов; в других браузерах их нужно задать отдельно. Одинаковые ключи
проектов используют одно название. Выделение позволяет удалить выбранные записи,
включая скрытые фильтром, после подтверждения с общим количеством отчётов.

Браузерная проверка проектов: `node tests/history-projects.browser.cjs`
проверяет фильтр, названия, перезагрузку, старые записи и узкий экран.
Для запуска нужен Playwright; `QA_REPORT_PLAYWRIGHT` может указывать на
уже установленный модуль, `QA_REPORT_SCREENSHOTS` — на папку для снимков.

### Выделение и удаление в истории

Кнопка с чекбоксом слева от фильтра проектов включает режим выделения.
Выбирайте отдельные чек-листы или «Выбрать всё» для записей в текущем списке.
Выбор сохраняется при поиске и смене проекта; счётчик отдельно показывает
записи, скрытые фильтром. Кнопка «Удалить выбранные» находится внизу окна
и запрашивает подтверждение с количеством чек-листов, включая скрытые.
Выход из режима или закрытие истории сбрасывает выделение.

При удалении облачного чек-листа удаляется и его локальная копия.
Если часть записей удалить не удалось, они остаются выбранными для повтора;
остальные удаляются. При удалении текущего чек-листа редактор открывает пустой.
Кнопка полной очистки убрана; удаляйте нужные чек-листы через выделение.
Кнопка «Сохранить снимок» убрана: чек-лист уже сохраняется автоматически
и при открытии истории, а комментарии — при вводе и потере фокуса.

### Сортировка и даты в истории

По умолчанию первыми показаны чек-листы с последними изменениями.
Список «Последние изменения / Дата создания» справа от счётчика переключает порядок; в обоих
случаях новые записи идут первыми. Карточка показывает даты создания и изменения
до минуты, полное время доступно при наведении. Выбор чек-листов сохраняется
при смене сортировки.

Дата изменения обновляется после изменения содержимого, статусов, структуры
чек-листа или комментария в истории. Открытие, просмотр, перезагрузка и повторное
сохранение того же содержимого её не меняют. Это правило действует для локальной
и облачной истории. У прежних записей сохранённая дата используется как исходная:
отделить прошлые просмотры от правок задним числом невозможно. Если старой записи
не хватает одной даты, отображается другая известная дата.

Браузерная проверка: `node tests/history-sorting.browser.cjs` с Playwright
(или путём в `QA_REPORT_PLAYWRIGHT`). Проверяются даты и порядок после просмотра,
правок и комментариев, обе сортировки, фильтры, выделение и узкий экран.

### Использовать историю

В модалке "История отчётов" можно:

- искать отчёты;
- видеть количество всех, облачных и локальных записей;
- видеть номер задачи или пометку «Без задачи»;
- видеть короткий public ID, дату и время сохранения;
- открыть сохранённую версию;
- создать копию;
- удалить запись;
- оставить комментарий к конкретному экземпляру.

История распознаёт номер задачи в ссылках разных трекеров, например
`/browse/QA-123` и `/project/Task/QA-123`, а также отдельно указанный ключ
`QA-123`. Ранее сохранённые записи отображаются правильно без повторного
сохранения. Если номер не распознан, показывается введённая ссылка; пометка
«Без задачи» остаётся только при пустом поле.

Комментарий хранится отдельно от содержимого чек-листа и не влияет на `contentHash`,
поэтому сам по себе не вызывает конфликт версий.

### Разрулить конфликт

Если облачное хранилище включено и облачная версия изменилась, под хедером появляется уведомление
"Есть изменения в облаке" с кнопкой "Сравнить".

В модалке сравнения можно:

- открыть облачную версию;
- оставить локальную и явно перезаписать облако;
- сохранить обе версии.

При сохранении обеих версий исходная облачная запись остаётся канонической и
сохраняет старый `publicId`. Локальная расходящаяся версия сохраняется как новая
копия с новым `publicId`; если пользователь выбирает открыть её, URL сразу
переключается на новый `/report/<id>`.

## Локальные вложения и приём результатов агента

Импорт по ссылке на Jira-комментарий предлагает сохранить изображения и файлы
в браузере в исходных ячейках. Компактная кнопка с контурным роботом в шапке
всегда открывает окно приёма. В светлой теме робот тёмный, как остальные иконки
хедера, а надписи ON/OFF контрастнее; в тёмной и графитовой темах робот белый.
Badge справа сверху показывает состояние сессии:
OFF — стандартный контур, как у кнопки Jira, без свечения; ON — зелёный контур с мягким пульсирующим
свечением контура и робота. Фон кнопки прозрачный. При уменьшении движения
в настройках устройства свечение остаётся слабым и статичным. Во время приёма
доступны «Остановить» и «Скопировать промпт», после остановки — «Включить приём».
Через временную сессию агент загружает файлы бинарными запросами и заполняет выбранные
ячейки. Облачное хранилище включать не требуется; успех подтверждается только
после сохранения отчёта с файлами в IndexedDB.

Контракт API, ограничения, обработка конфликтов и примеры запросов описаны в
[инструкции по локальному импорту](docs/local-import.md).

## Импорт Чек-листов

### Ручной импорт Jira Wiki Markup

Кнопка «Импорт» в хедере открывает вставку готовой разметки без подключения к Jira.

Поддерживается:

- вставка Jira Wiki Markup напрямую;
- несколько таблиц в одном комментарии;
- разделы `h2.` / `h3.`;
- разные наборы колонок в разных таблицах;
- Jira-цвета статусов;
- встроенное форматирование, ссылки с вложенными или экранированными квадратными скобками и цвета в hex-формате или стандартных именах Jira;
- кодовые блоки Jira;
- изображения по имени вложения, если они приходят из Jira-комментария вместе со списком вложений.

### Импорт по ссылке на комментарий Jira

Пункт «Jira → Отчёт из комментария» открывает ввод прямой ссылки. Приложение:

1. определяет настроенную Jira по адресу комментария и использует OAuth-подключение текущего пользователя;
2. читает комментарий через Jira REST API;
3. подтягивает список вложений задачи, если хватает прав;
4. парсит Jira Wiki Markup;
5. предлагает выбрать пункты и добавить их в текущий чек-лист либо заменить его.

### Входящий импорт из QA Assistant

QA Assistant может отправить чек-лист в QA Report через API:

```bash
curl -X POST http://localhost:4173/api/checklists/import \
  -H 'Content-Type: application/json' \
  -d '{
    "source": "qa-assistant",
    "format": "jira",
    "title": "Экспорт транзакций в Excel",
    "issueKey": "https://company.atlassian.net/browse/ADVINTAUT2-117",
    "content": "||Номер||Проверка||Как проверить||Ожидаемый результат||Фактический результат||Статус||Комментарий||\n|1.|Отображение кнопки Export|Авторизоваться как Admin|Кнопка Export видна и доступна для нажатия| | | |"
  }'
```

Этот запрос выполняется backend-сервисом QA Assistant без пользовательской cookie
и без отдельного service token. Endpoint создаёт только временный payload; он не
создаёт пользовательский отчёт и не действует от имени пользователя.

Поля:

| Поле | Обязательное | Описание |
| --- | --- | --- |
| `format` | да | Пока поддерживается только `jira` |
| `content` | да | Jira Wiki Markup таблицы или чек-листа |
| `source` | нет | Источник, например `qa-assistant` |
| `title` | нет | Название импортируемого чек-листа или первого раздела |
| `issueKey` | нет | Для текущего сценария сюда передаётся полная ссылка на Jira-задачу |

Несмотря на имя `issueKey`, для входящего импорта поле используется как ссылка на
задачу. Передавайте полный URL:

```text
https://company.atlassian.net/browse/ADVINTAUT2-117
```

Успешный ответ:

```json
{
  "ok": true,
  "checklistId": "ec8d6464-70e0-4c84-ba6e-31fbd7fd1c9f",
  "publicId": "851a9bd2",
  "url": "https://qa-report.company.ru/report/851a9bd2?importToken=ec8d6464-70e0-4c84-ba6e-31fbd7fd1c9f",
  "expiresAt": 1783285561851,
  "parsed": {
    "sections": 1,
    "rows": 15
  }
}
```

Дальше нужно открыть `url` в браузере. По этой ссылке QA Report заберёт payload
с сервера под AD-сессией пользователя, создаст новый чек-лист и очистит `importToken`
из адресной строки. Если пользователь ещё не вошёл, QA Report сначала покажет форму
входа и после успешной авторизации вернёт его на исходную ссылку.

Публичный origin для `url` берётся из `QA_REPORT_PUBLIC_URL`, `APP_PUBLIC_URL`
или `PUBLIC_URL`, если переменная задана. Если переменной нет, сервер использует
`Forwarded` или `X-Forwarded-Proto` + `X-Forwarded-Host`; без них будет использован
обычный `Host` запроса, например `localhost:4173` при локальном вызове.

Ошибки:

| Код | Когда возвращается |
| --- | --- |
| `400` | `format` не равен `jira` |
| `400` | `content` пустой или не строка |
| `422` | Jira-разметку не удалось распарсить в пункты чек-листа |
| `404` | import token не найден или истёк |

Payload входящего импорта хранится в SQLite 15 минут и удаляется после истечения TTL.
Jira-разметка не передаётся через query string; в URL находится только короткий
import token.

| --- | --- | --- |
| Jira Data Center 7.3.2 | Jira Wiki Markup | Персональный OAuth 1.0a access token |

`Authorization` не является источником credentials.

### Публикация комментария

Кнопка справа от «Чек-лист» публикует отчёт в Jira. После первой успешной
публикации она меняется на «Обновить отчёт» и обновляет связанный комментарий.
То же действие доступно в меню «Экспорт». В меню со стрелкой рядом с кнопкой
выберите «Опубликовать заново», чтобы создать новый комментарий: прежний
остаётся в задаче, а отчёт связывается с новой публикацией.

Под кнопкой и в карточке истории доступны ссылка на комментарий, дата и время
первой отправки и последнего обновления. Время показывается в часовом поясе
браузера. Связь сохраняется вместе с отчётом локально и, если включена серверная
история, в облачной копии. При создании копии отчёта или открытии файла .report
она не переносится. Смена задачи предлагает новую публикацию; возврат к прежней
задаче снова позволяет обновить прежнюю связь.

Если при обновлении Jira сообщает, что связанный комментарий удалён или недоступен,
приложение сбрасывает эту связь, ссылку и даты публикации. Кнопка меняется на
«Опубликовать отчёт»; новый комментарий появится только после явной отправки.
Сброс сохраняется локально и в облачной истории, если она включена; отмена правок
не восстанавливает исчезнувший комментарий. Дата создания чек-листа сохраняется,
дата изменения отмечает момент обнаружения потери связи. Другие ошибки доступа,
временная недоступность Jira и обычный ответ «не найдено» связь не сбрасывают.

Обновлять можно только комментарий текущего пользователя Jira. Если комментарий
удалён, недоступен или изменён непосредственно в Jira, приложение показывает
причину и не создаёт замену автоматически. При обновлении сохраняется прежнее
ограничение видимости комментария. Выбор разделов и статусов начинается с состава
предыдущей публикации; выбранный состав полностью заменяет текст комментария.
Уже опубликованные комментарии не привязываются автоматически при импорте.

Для больших отчётов сохраняются ссылки на все части. Успешные части и результаты
их обновления сохраняются по мере отправки; частично завершённая операция
помечается в отчёте. При изменении числа частей нужно выбрать «Опубликовать заново».
Комментарий, который стал слишком большим для обновления, также требует новой
публикации. После неопределённого результата создания приложение не повторяет
запрос автоматически; повтор обновления проверяет уже записанное содержимое.

Перед публикацией обязательна полная ссылка на конкретную задачу. Если поле
«Ссылка на задачу» пустое или в ссылке нет ключа задачи, стандартное окно
предлагает «Заполнить ссылку» и переводит фокус к полю. Проверка подключения,
выбор состава отчёта и загрузка вложений начинаются только после исправления.
Ссылка повторно проверяется после выбора состава отчёта.

Перед отправкой и обновлением отчёта обычный текст преобразуется для Jira:
фигурные скобки заменяются квадратными, например `/items/{id}` → `/items/[id]`.
В Wiki Markup новые квадратные скобки экранируются, чтобы Jira показывала
их как текст. Замена действует в описании, окружении, заголовках, ячейках
и подписях ссылок. В блоках и фрагментах кода, адресах ссылок и именах
вложений исходные скобки сохраняются. Текст в редакторе, сохранённом отчёте,
предпросмотре и при обычном копировании не изменяется.

При публикации приложение:

1. берёт полную ссылку из поля "Ссылка на задачу";
2. извлекает ключ задачи из URL;
3. готовит комментарий в нужном формате;
4. загружает локальные вложения в Jira;
5. создаёт комментарий;
6. проверяет, что комментарий создан и читается обратно.

Если Jira или промежуточный proxy возвращает успешный HTTP-статус без объекта
комментария, приложение пытается найти созданный комментарий среди последних
комментариев задачи. При ошибке показываются диагностические детали: upstream
HTTP-статус, `Location`, краткое тело ответа, количество комментариев до и после
публикации и ошибки контрольного чтения.

### Вложения

- приложение читает существующие вложения задачи;
- выбирает свободное имя `screenshot-N.png`;
- вставляет изображения в комментарий как `!screenshot-N.png|thumbnail!`;
- если список вложений недоступен, к имени добавляется временная метка.

Перед отправкой приложение проверяет сигнатуру изображения, MIME-тип и расширение.
Файлы загружаются по одному, чтобы проще диагностировать ошибку конкретного вложения.

### WAF / SSO / Browser Challenge

Если корпоративный WAF или SSO возвращает HTML browser challenge вместо JSON Jira
REST API, приложение останавливает публикацию до POST и возвращает
`JIRA_SECURITY_CHALLENGE`.

Для серверной интеграции администратору нужно разрешить исходящий IP приложения
либо исключить `/rest/api/*` из интерактивной browser-проверки при наличии
корректного `Authorization` header.

Cookie браузерной Jira-сессии приложение не копирует и не сохраняет.

## Корпоративное Файловое Хранилище

Корпоративная версия поддерживает приватное S3-совместимое хранилище MinIO.
Пользователь не управляет подключением и не видит ключи. Для изображений и
файлов доступно действие «Загрузить в хранилище»; после загрузки Base64 заменяется
ссылкой на защищённый маршрут QA Report.

При включённой серверной истории вложения переносятся в MinIO автоматически до
сохранения отчёта в SQLite. Слева сверху на изображении или файловой карточке
показывается состояние: индикатор загрузки для локального объекта и облако для
объекта, уже сохранённого в MinIO. Превью изображения при автоматической
миграции сохраняется и загружается по удалённой ссылке.

Ручной сценарий отделён от автоматического. До загрузки в контекстном меню есть
пункт «Загрузить в хранилище». После успешной загрузки он заменяется пунктом
«Заменить на ссылку», который по явному выбору пользователя заменяет превью или
файловую карточку обычной кликабельной ссылкой.

При экспорте Jira Wiki Markup объекты MinIO преобразуются в ссылки вида
`[название|URL]`, а не в синтаксис Jira-вложения.

Объекты размещаются по ID отчёта:

```text
reports/<ownerHash>/<reportId>/report.json
reports/<ownerHash>/<reportId>/images/<uuid>-<filename>
reports/<ownerHash>/<reportId>/files/<uuid>-<filename>
```

Настройка выполняется только на сервере:

| Переменная | Назначение |
| --- | --- |
| `QA_STORAGE_ENDPOINT` | HTTPS endpoint MinIO |
| `QA_STORAGE_BUCKET` | Имя корпоративного бакета |
| `QA_STORAGE_REGION` | S3-регион, для MinIO обычно `us-east-1` |
| `QA_STORAGE_ACCESS_KEY_FILE` | Путь к secret-файлу с access key |
| `QA_STORAGE_SECRET_KEY_FILE` | Путь к secret-файлу с secret key |
| `QA_STORAGE_ACCESS_KEY` | Access key для локальной разработки через игнорируемый `.env` |
| `QA_STORAGE_SECRET_KEY` | Secret key для локальной разработки через игнорируемый `.env` |
| `QA_JIRA_ALLOWED_ORIGINS` | Разрешённые Jira origin через запятую; произвольные адреса запрещены |
| `QA_REPORT_TRUST_PROXY` | Разрешает учитывать `Forwarded`/`X-Forwarded-*` только за доверенным proxy |

Значения ключей нельзя хранить в репозитории или передавать в браузер.
Объекты разделяются хешем корпоративного email из проверенной сессии, поэтому
одинаковые ID отчётов разных пользователей не дают доступ к чужим файлам.

Для локальной настройки используйте файл `.env` в корне проекта. Он уже создан,
исключён через `.gitignore` и содержит пустые поля для ключей. После изменения
`.env` необходимо перезапустить `npm start`. `.env.example` служит безопасным
шаблоном без секретов.

## Защита Web-интерфейса

- Импортируемая Jira-разметка проверяет URL и разрешает в ссылках только `http` и `https`.
- Форматированный HTML отчётов очищается по списку разрешённых элементов и атрибутов до отображения и сохранения.
- Сервер удаляет исполняемые HTML-элементы и обработчики событий перед записью отчёта в SQLite.
- Сервер устанавливает CSP и защитные HTTP-заголовки, запрещает cross-site изменения и ограничивает частоту API-запросов.

## Хранение Данных

| Данные | Где хранятся |
| --- | --- |
| Текущий черновик | `localStorage` браузера |
| Локальный кэш истории | IndexedDB браузера |
| Серверная история отчётов | SQLite-файл `reports-data/qa-report.sqlite`, используется только если пользователь включил облачное хранилище |
| Public ID экземпляра | SQLite и локальный кэш |
| Комментарий истории | SQLite для облачных записей, IndexedDB для локальных |
| Настройки Jira без секрета | `localStorage` браузера |
| Jira token / пароль | Только память открытой вкладки |
| Изображения и файлы облачных отчётов | MinIO, в SQLite сохраняются ссылки и метаданные |
| Входящий импорт QA Assistant | SQLite, автоматически удаляется через 15 минут |

По умолчанию чек-листы сохраняются только локально в браузере. Если пользователь
включил "Сохранять чек-листы в облачном хранилище", локальные Base64-вложения
сначала загружаются в MinIO. После этого серверная история хранит в
`document_json` документ со ссылками и метаданными, а `report.json` сохраняется в
директории отчёта в MinIO. Бинарные данные в SQLite не записываются.

Метаданные вынесены в отдельные колонки: название, ссылка на Jira-задачу, ключ
задачи, окружение, общий статус, даты, владелец, `public_id`, `content_hash`,
`history_comment` и `deleted_at`.

Старые записи без `public_id` получают его при миграции или первом чтении.

## Защита От Конфликтов

В интерфейсе используются два понятия:

- локальная версия - копия чек-листа в текущем браузере;
- облачная версия - копия чек-листа в серверной истории SQLite.

При сохранении фронтенд отправляет последний известный `contentHash`. Если
облачная версия уже изменилась и hash не совпадает с базовым hash клиента,
backend возвращает `409 Conflict` и не перезаписывает документ.

`contentHash` считается по нормализованному содержимому чек-листа. В него не входят:

- `updatedAt`;
- `revision`;
- `lastSavedBy`;
- `lastSavedClientId`;
- UI-состояние фокуса, скролла и выбранной ячейки;
- комментарий записи в истории.

Такой механизм защищает от сценария, когда один и тот же отчёт открыт на двух
компьютерах: старая вкладка не сможет молча затереть более новую облачную версию.

## Как Определяется Владелец Истории

Единственный источник владельца — нормализованный корпоративный email из проверенной
серверной сессии. Backend добавляет условие владельца непосредственно в SQL для чтения,
изменения и удаления. Чужой объект возвращает `404`. Ключ пространства может выбрать
отдельное пространство синхронизации только внутри этого владельца, но не позволяет
получить историю другого корпоративного пользователя. Остальные browser headers,
query/body поля, client ID и IP не могут изменить владельца; anonymous fallback удалён.

## Конфигурация

| Переменная | Назначение |
| --- | --- |
| `PORT` | Порт Node-сервера, по умолчанию `4173` |
| `HOST` | Host для `server.listen`, по умолчанию `127.0.0.1`; в Docker используется `0.0.0.0` |
| `QA_REPORT_PUBLIC_URL` | Публичный origin для ссылок импорта, например `https://qa-report.company.ru` |
| `APP_PUBLIC_URL` / `PUBLIC_URL` | Альтернативные имена переменной публичного origin |
| `REPORTS_DB_PATH` | Путь к SQLite-файлу истории |
| `QA_REPORT_STORE_ATTACHMENTS` | Если `true`, сервер снова будет хранить embedded изображения и file-card в SQLite; по умолчанию выключено |
| `QA_STORAGE_*` | Настройки корпоративного MinIO, описанные выше |
| `QA_JIRA_ALLOWED_ORIGINS` | Разрешённые Jira origin через запятую |
| `QA_REPORT_TRUST_PROXY` | Доверие transport-заголовкам proxy |
| `QA_REPORT_MAX_BODY_MB` | Максимальный размер JSON-запроса к backend, по умолчанию `150` |
| `QA_REPORT_MAX_ATTACHMENT_MB` | Максимальный размер одного вложения Jira, по умолчанию `50` |

Для публичного сервера рекомендуется задать `QA_REPORT_PUBLIC_URL`, даже если
reverse proxy передаёт `Forwarded` или `X-Forwarded-*`. Это убирает риск, что API
импорта вернёт внутренний `localhost` или адрес контейнера.

Если приложение стоит за Nginx/Caddy/Traefik, лимит тела запроса на reverse proxy
должен быть не ниже `QA_REPORT_MAX_BODY_MB`. Для Nginx обычно нужен
`client_max_body_size 150m;` или больше для endpoint `/api/jira/attachments`.

## Docker

Запуск:

```bash
docker compose up -d --build
```

Приложение будет доступно:

```text
http://127.0.0.1:4173
```

Изменить внешний порт можно через `.env`:

```env
APP_PORT=8080
```

Для публичного URL импорта:

```env
QA_REPORT_PUBLIC_URL=https://qa-report.company.ru
```

SQLite-файл серверной истории хранится в volume `reports_data`.

Путь к SQLite можно переопределить:

```env
REPORTS_DB_PATH=/app/reports-data/qa-report.sqlite
```

Для бэкапа достаточно сохранять volume `reports_data` или сам файл
`qa-report.sqlite` вместе с `-wal`/`-shm` файлами, если они есть рядом.

Проверка:

```bash
docker compose ps
curl http://localhost:4173/api/health
```

Логи:

```bash
docker compose logs -f qa-report
```

Остановка:

```bash
docker compose down
```

Публиковать Node.js-порт напрямую запрещено. По умолчанию Compose привязывает его
только к `127.0.0.1`. Для корпоративного развертывания обязателен HTTPS reverse
proxy или ingress (Nginx, Caddy, Traefik) с валидным сертификатом. Флаги доверия
к forwarded- и SSO-заголовкам можно включать только когда прямой доступ к Node.js
закрыт, а proxy перезаписывает эти заголовки.

## Проверки

Синтаксическая проверка:

```bash
npm run check
```

Интеграционный тест:

```bash
npm test
```

Тест поднимает локальную имитацию Jira, запускает `server.js` на отдельном порту
и проверяет:

- обязательную сессию для страниц и API;
- игнорирование поддельных identity headers;
- изоляцию SQLite-истории между двумя email;
- OAuth-подключение одной из двух Jira, RSA-SHA1 подпись от пользователя и изоляцию tokens между email;
- CSRF logout и удаление session cookie;
- LDAPS/TLS/CA/server-name проверки, LDAP escaping и закрытие соединений;
- session expiry/secret rotation, rate limits и отсутствие auth bypass;
- публичное создание временного импорта и обязательную AD-сессию для открытия ссылки;

## Известные Ограничения

- Входящий импорт из QA Assistant хранится временно в SQLite и удаляется после TTL.
- Вложения облачной истории требуют доступного и настроенного MinIO. В SQLite
  сохраняются только ссылки и метаданные.
- Stateless-сессия не отзывается мгновенно при отключении пользователя в AD; окно ограничено 8 часами.
- SQLite рассчитан на один сервер/контейнер. Для горизонтального масштабирования
  нужен переход на PostgreSQL или другое внешнее хранилище.
- Итоговое отображение Jira Wiki Markup зависит от конкретной версии и настроек
  Jira Data Center / Server.
- Корпоративные WAF/SSO могут блокировать серверные Jira REST-запросы.
- OAuth-токены Jira хранятся только на сервере в зашифрованном виде.

## Правила описания изменений в «Что нового»

Каждая заметная пользователю доработка описывается в текущей записи `release-notes.js`.
Изменения за одну дату добавляются в один релиз. Версии обеих сборок должны совпадать.

### Как писать для конечного пользователя

«Что нового» читают люди, которые ведут чек-листы и отчёты, а не разработчики
приложения. Каждый пункт должен отвечать хотя бы на один вопрос: что теперь
можно сделать, что стало удобнее или какая заметная проблема исправлена.

- Описывать результат в привычных пользователю словах. Названия кнопок и разделов
  приводить ровно как в интерфейсе, если это помогает найти функцию.
- Один пункт — одна понятная мысль, обычно одно короткое предложение. Не более
  200 символов; связанная инструкция допустима только если без неё трудно
  воспользоваться изменением.
- Не включать имена файлов и функций, внутренние идентификаторы, библиотеки,
  служебные версии, устройство кеша, протоколы, результаты тестов, логи, команды
  и подробности реализации. Термины, знакомые пользователю по интерфейсу
  (Jira, HTML, PWA), допустимы, если нужны для понимания действия.
- Рефакторинг, тесты, сборку и другие внутренние работы без заметного эффекта для
  пользователя оставлять в технической документации и истории разработки.
- Для исправления назвать прежнюю проблему и результат; для новой возможности
  или улучшения — доступное действие или конкретное удобство. Не писать
  «различные улучшения», «улучшена стабильность» и другие неопределённые обещания.
- Не раскрывать внутренние адреса, данные пользователей и сведения о компании.
  Не описывать неподтверждённые возможности и будущие планы как готовые функции.
- Перед завершением задачи перечитать новые пункты глазами пользователя,
  объединить повторы и убрать всё, что не помогает работе с приложением.
  Проверка длины в `npm run check` не заменяет эту редакторскую проверку.

Пример: вместо «Изменён обработчик click у anchor в contenteditable» —
«Ссылки в ячейках можно открыть отдельной кнопкой, изменить их адрес и название».
Вместо «Добавлена проверка поколений записи IndexedDB» —
«Статус сохранения больше не скрывает новые несохранённые правки».

## Устанавливаемая корпоративная PWA

После входа приложение можно установить средствами поддерживающего браузера
(Chrome/Edge на Windows, macOS и Linux). Нужен HTTPS или localhost для теста.
Цвет панели приложения следует теме устройства. Новая версия загружается в фоне;
рядом с «Что нового» появляется «Обновить». Перед переключением чек-лист сохраняется
в IndexedDB. Ошибка сохранения, публикация, обработка вложений или открытый диалог
блокируют перезагрузку. Другие окна приложения требуется предварительно закрыть.
Обновления проверяются при запуске, возвращении в окно, восстановлении связи и
каждые 15 минут в видимом окне. Автоматическое применение без кнопки происходит
после закрытия всех окон текущей версии.

Схема корпоративной авторизации не менялась: HTML редактора, login и API не
кэшируются. Каждое открытие страницы доходит до существующей серверной проверки
сессии; сохранённые ресурсы не подменяют отказ в доступе. При отсутствии связи
новое окно показывает сообщение о необходимости подключения, а не редактор.
Это намеренное отличие от автономной персональной PWA: автономный вход потребовал
бы отдельного изменения политики авторизации. Очередь офлайн-синхронизации не добавлена.
Jira OAuth, MinIO, CSRF, LDAP, сроки сессий и разграничение владельцев сохранены.
Локальный агент, Google Drive, Яндекс.Диск и внешняя обратная связь не переносились.

При изменении ресурсов увеличивайте CACHE_NAME в sw.js и актуализируйте SHELL.
Не добавляйте HTML, API, токены или документы в этот кэш. Docker-сборка включает
манифест, worker и иконки. Тесты PWA проверяют отказ при недоступном сервере,
сохранение редиректов авторизации и запрет обновления при нескольких окнах.

Локальный стенд запускается только на loopback с NODE_ENV=development и уже
существующими DEV_LOGIN_EMAIL / DEV_LOGIN_PASSWORD. Используйте отдельный
REPORTS_DB_PATH и случайный AUTH_SECRET; пароли стенда не записывайте в репозиторий.

### Компактное обновление в хедере

При готовности новой версии появляется кнопка с круговыми стрелками и цветной точкой. Подсказка при наведении объясняет действие; нажатие сохраняет чек-лист и запускает штатное обновление. На узких экранах подписи действий заменяются иконками, а панель действий при необходимости прокручивается горизонтально, не перекрывая Jira.

## Окружение

В новом чек-листе «Окружение» и «Итог» остаются пустыми. Перед публикацией
нужно указать окружение и выбрать итог проверки. При попытке публикации пустые
поля подсвечиваются с подсказками; после заполнения подсветка снимается.
Сохранение черновика, предпросмотр и экспорт доступны до заполнения этих полей.
Заполненные значения в существующих чек-листах сохраняются.

В Настройки → «Окружение» можно добавить, переименовать и удалить значения,
включая DEV, STAGE и PROD по умолчанию. Изменения применяются кнопкой «Сохранить»
и появляются в списке поля «Окружение». Закрытие настроек без сохранения отменяет
правки. Список хранится в текущем браузере отдельно для каждого пространства;
ранее введённые окружения доступны при первом открытии нового раздела.
Удаление или переименование варианта не меняет существующие чек-листы.
Стрелка в поле «Окружение» открывает весь сохранённый список независимо от
текущего значения. Выбор сразу заменяет текст в поле. При ручном вводе список
показывает совпадающие варианты; произвольный текст не добавляется в список
автоматически. Стрелки вверх и вниз выбирают вариант, Enter применяет его,
Esc закрывает список. Можно удалить все варианты и заполнить поле вручную.

## Столбцы по умолчанию и сортировка строк

В «Настройки → Чек-лист → Столбцы» набор для новых чек-листов и разделов редактируется горизонтальными карточками: добавление, переименование, удаление, перетаскивание и компактные действия с иконками. Во время перетаскивания вертикальная линия показывает точное место вставки слева или справа от карточки. После перемещения кнопкой карточка подсвечивается и остаётся в видимой области. Компактные карточки «№» и «Статус» отмечены замком и неизменяемы. Исходный набор — Проверка, Ожидаемый результат, Фактический результат, Комментарий; его можно восстановить кнопкой. Подсказки и действия оформлены так же, как в остальных разделах настроек. Набор сохраняется кнопкой «Сохранить» в текущем браузере. Существующие отчёты и столбцы импортируемых таблиц не перестраиваются.

В меню «•••» каждого столбца, кроме номера, доступно «Очистить столбец». Команда очищает все ячейки только этого столбца в текущем разделе, включая текст и вложения; сам столбец сохраняется. Для столбца «Статус» все строки получают «НЕ ПРОВЕРЕНО». Очистку можно отменить и повторить одним действием; соседние столбцы и другие разделы не меняются.

В меню заголовка «Статус» доступны «Сортировать по статусу» и «Вернуть исходный порядок». Сортировка действует на строки отдельного раздела: НЕ ОК → ТРЕБУЕТ УТОЧНЕНИЯ → ПОЧТИ ОК → ЧАСТИЧНО ПРОВЕРЕНО → OK → НЕ ПРОВЕРЕНО. Новые строки со статусом «НЕ ПРОВЕРЕНО» поэтому остаются внизу. Одинаковые статусы сохраняют исходную последовательность. Это представление редактора: исходные номера, порядок публикации и экспорта сохраняются. Режим сохраняется вместе с разделом.

В отсортированном разделе скрыт захват строки, отключены перемещение вверх/вниз, разделение «отсюда», вставка выше/ниже; перенос из такого раздела или в него, включая массовый, заблокирован. Столбцы можно перемещать. Новые строки добавляются нижней кнопкой, дубликаты — командой меню: в исходном порядке они помещаются в конец. Изменение статуса пересортировывает отображение. Возврат исходного порядка сохраняет правки, новые строки и удаления.

Перерисовка таблицы после изменения статуса, сортировки, добавления строки или столбца сохраняет горизонтальную позицию каждого раздела и вертикальную позицию страницы. Редактор не возвращает пользователя к первому столбцу.

Создание сессии приёма от агента требует действующей пользовательской сессии и
CSRF-токена. Агент использует отдельный `X-QA-Import-Token` только для выданной
сессии; пользовательская cookie и Jira OAuth credentials ему не передаются.
Заголовок проходит через существующий reverse proxy без изменения правил
корпоративной авторизации. Загрузка вложений из Jira подписывается персональным
OAuth-подключением пользователя и проверяет принадлежность файла задаче.

В окне импорта Jira опция вложений выделена крупным чекбоксом и подписью о сохранении в браузере. Кнопка «Импортировать» показывает индикатор загрузки; отдельная полоса отражает этап получения комментария, количество обработанных уникальных вложений и сохранение. Ошибки файлов выводятся отдельно. Во время операции поля и повторный запуск заблокированы.

## Выбор и повторное использование вложений Jira

При вставке Jira-разметки файлы не скачиваются: окно показывает ссылки по колонкам, а в отчёте они остаются метками Jira. Исходные имена и параметры сохраняются при редактировании, перезагрузке и экспорте: `!screenshot-4.png|thumbnail!` и `[^log.txt]`. Вертикальная черта внутри изображения не разделяет колонки. Проверка наличия файлов не выполняется; при публикации по имени они должны уже существовать в целевой задаче Jira. Для скачивания и проверки используйте импорт по ссылке на комментарий. Если такое скачивание не удалось, ссылка также сохраняется, а причина показывается в предупреждении.

Импорт выполняется в два шага: «Продолжить» получает текст комментария и список вложений без скачивания файлов, затем «Импортировать» загружает файлы выбранных колонок. Выбор раздельный по разделам; описание учитывается отдельно. Состав пунктов, содержимое колонок и перенос файлов настраиваются перед импортом. Файлы с действием «Оставить ссылки на Jira» сохраняются карточками «В Jira» с возможностью дозагрузить их в браузер. Счётчик учитывает уникальные вложения.

Браузерная регрессия: `node scripts/test-markup-references.cjs` с установленным Playwright (или путём к нему в `QA_REPORT_PLAYWRIGHT`). Тест запускает изолированный локальный сервер и подменяет обращения к Jira, проверяет импорт, редактирование, перезагрузку, разметку публикации и сохранение ссылок при недоступном скачивании.

Исходные задача, идентификатор и имя файла сохраняются вместе с отпечатком локальной копии. Перед публикацией `/api/jira/attachment-manifest` через существующее подключение проверяет список файлов целевой задачи. Неизменённые вложения той же задачи используются повторно. Файлы, для которых не найдена подтверждённая копия в целевой задаче, загружаются. Удалённое вложение восстанавливается из локальной копии, если она есть; иначе публикация останавливается с ошибкой. Отказ доступа не считается отсутствием файла. При конфликте имён добавляется суффикс; для одноимённых существующих вложений используются точные ссылки.

Проверка существующих вложений не скачивает файлы из Jira: достаточно одного
списка вложений задачи, сохранённого ID и отпечатка локальной копии. Старый
формат ID/имя/URL без задачи и отпечатка тоже распознаётся: ID должен присутствовать
в списке целевой задачи, а сохранённая ссылка — совпадать с её ссылкой на файл;
при наличии размера он проверяется по локальным данным. Если задача источника
указана явно, она должна совпадать с целевой. При первом таком использовании
локальный отпечаток и сведения о задаче сохраняются в новом формате.

Подтверждённые связи дополнительно сохраняются в документе отчёта в
`jiraAttachmentLinks`, отдельно от HTML. Список содержит только локальный ID,
задачу, ID Jira, имя, ссылку и отпечаток; байты файлов туда не копируются. При
утрате HTML-атрибутов связь восстанавливается по локальному ID и отпечатку,
без скачивания из Jira. Разные версии содержимого и задачи имеют свои записи.
Если утрачены и исходная связь, и эта запись, совпадение имени не считается
доказательством: неоднозначное обновление останавливается с предложением
восстановить вложение импортом из связанного комментария. Новый файл с тем же
именем можно загрузить, когда прежний файл уже известен по сохранённой записи.
Автоматические повторы загрузки отключены: потеря ответа не означает, что Jira
не получила файл. Список вложений другой задачи отклоняется.

Связи с подтверждёнными вложениями сохраняются при отмене и повторе правок:
обновление комментария не загружает заново неизменённые файлы. При отмене
изменения содержимого файла возвращается связь именно с его прежними байтами;
при возврате к другой задаче сохраняются её собственные связи с вложениями.
Браузерная проверка `node tests/jira-attachment-reuse.browser.cjs` воспроизводит
публикацию и обновление с настоящим планированием загрузок на синтетических
ответах Jira, отмену/повтор, перезагрузку, изменение файла, удаление вложения
из Jira, смену задачи и восстановление связей 27 старых файлов одним запросом
списка, без скачивания содержимого и повторной загрузки. Также проверяются
восстановление по отдельным записям, потеря всех связей, ошибки доступа и список
вложений другой задачи без отправки файлов и комментариев. Для запуска нужен `QA_REPORT_PLAYWRIGHT`.


Перед отправкой показано «Используем повторно» — число распознанных вложений отчёта, а не общее число файлов в Jira, — и сколько будет загружено. Связь с каждым подтверждённым вложением сохраняется до публикации комментария, поэтому повтор после ошибки комментария не создаёт новые копии.


## Абзацы и курсор рядом с изображениями и кодом

Клик по узкой области у левого края изображения или блока кода ставит обычный текстовый курсор перед объектом. Shift+Enter в этой позиции добавляет строку перед блоком, сдвигает его ниже и позволяет сразу вводить текст. Для клавиатуры: сфокусируйте объект, используйте стрелку влево или вправо для перехода к его границе, затем Shift+Enter. Клик по основной области по-прежнему открывает изображение или редактор кода. Пустая строка перед новым объектом заранее не добавляется; уже введённые пользователем отступы сохраняются.

Экспорт в Jira различает текстовые строки, пустые строки и абзацы редактора. Переносы формируются после экранирования текста, отделяются от изображения пробелом и не проходят повторное экранирование. Изображения, ссылки и код сохраняют собственную разметку; в списках экранируются текстовые разделители ячеек. Буквальная обратная косая черта передаётся как `&#92;`, чтобы не стать переносом. Внутренние переносы и разделители блока кода не меняются.

Оператор `!=` в тексте, описании, заголовках и подписях ссылок автоматически экранируется при экспорте в Jira: в разметку попадает `\!=`, а в отчёте сохраняется `!=`. Повторный импорт и экспорт не добавляют лишние обратные косые черты. Адреса ссылок, имена вложений и содержимое блоков кода сохраняются без замены оператора. Пользователю не нужно заменять его на «НЕ».

Браузерная регрессия: `node scripts/test-paragraphs.cjs` с установленным Playwright (или путём в `QA_REPORT_PLAYWRIGHT`). Проверяются реальные Enter/Shift+Enter, цветные абзацы, изображения, списки, код, обратный импорт таблицы, нативный курсор у границ объектов, ввод текста, открытие просмотрщика и сохранение после перезагрузки. Проверки используют локальные данные; финальное отображение в конкретной Jira зависит от её wiki-renderer.


## Размер вложений при публикации в Jira

При выборе файлов (включая вставку из буфера) под панелью форматирования видны
лимиты QA Report и целевой Jira. Размер сравнивается в байтах с исходным файлом.
Сервер запрашивает `GET /rest/api/2/attachment/meta` у подключённой Jira
Data Center/Server через персональное OAuth-подключение. Проверяются `enabled` и `uploadLimit`.
Если метаданные недоступны, интерфейс явно показывает неизвестный лимит Jira;
локальное редактирование остаётся доступным, а загрузку проверит сама Jira.

По умолчанию QA Report разрешает 50 МиБ на файл и 150 МиБ на JSON-запрос.
Это собственные настраиваемые ограничения приложения, а не ограничения Jira.
`QA_REPORT_MAX_ATTACHMENT_MB` управляет локальным пределом; интерфейс получает
его с сервера. Если Jira разрешает более крупные файлы, администратор может
увеличить этот предел вместе с `QA_REPORT_MAX_BODY_MB` и лимитом reverse proxy.
Браузерное хранилище также должно иметь достаточно свободного места.

Новые вложения проверяются перед первой загрузкой; уже существующие в Jira
файлы повторно не ограничиваются. Каждый файл отправляется отдельным JSON-запросом;
base64 занимает `4 × ceil(размер_файла / 3)` байт, плюс поля JSON и настройки
подключения. Перед отправкой проверяется точный размер сериализованного запроса
в UTF-8. На стороне Jira файл передаётся как исходные байты в multipart/form-data,
поэтому base64 не расходует лимит `uploadLimit` самой Jira.

HTTP 413 от прокси QA Report, ограничение самого приложения и отказ Jira
показываются раздельно. HTML-ответ 413 от Jira/proxy больше не считается страницей
проверки входа. Повторы загрузки автоматически не выполняются, чтобы избежать
дубликатов при потере ответа.

Настройка Nginx и диагностика: [инструкция по лимитам](docs/jira-upload-limits.md).

Браузерная проверка сценария: `node scripts/test-upload-limits.cjs` с Playwright
(или путём к установленному пакету в `QA_REPORT_PLAYWRIGHT`). Все Jira-запросы
в этом тесте подменены; реальные задачи не изменяются.

## Ручная нумерация и импорт для ретеста

Режим «Вручную — для ретеста» фиксирует текущие номера и делает столбец «Номер»
редактируемым. Удаление, сортировка и перенос строк или разделов не меняют номера
оставшихся пунктов: после удаления 4 остаются 1, 2, 3, 5. Новые и дублированные
строки получают пустой номер для ручного заполнения. Номер (`manualNumber`)
сохраняется вместе со строкой, в истории, при перезагрузке и во всех форматах экспорта.
Возврат к автоматическому режиму пересчитывает номера по порядку строк.

При замене чек-листа из разметки или комментария с колонкой номера доступен включённый по
умолчанию флажок «Сохранить исходную нумерацию». Он включает ручной режим;
снятие флажка пересчитывает номера в текущем автоматическом режиме (с 1 в каждом
разделе, если до импорта был ручной). Импорт из QA Assistant предлагает сохранить
номера, пересчитать их или отменить импорт. Без колонки номера сохраняется текущий
режим; в ручном режиме номера новых пунктов остаются пустыми.


### Импорт разметки и комментариев Jira

Кнопка «Импорт» в хедере открывает вставку готового чек-листа в формате
Jira Wiki Markup — например, полученного от ИИ. Подключение к Jira для разметки
не требуется. «Jira → Отчёт из комментария» открывает тот же импорт на вкладке
«Комментарий Jira». Форматы обычного текста и Markdown этим изменением не добавляются.

Можно вставить отдельные строки `|…|` без строки заголовков `||…||`.
Для такого фрагмента сразу предлагается добавление в существующий раздел;
единственный раздел выбирается автоматически. Номер в первом столбце и статус
в последнем распознаются предварительно: их назначение можно изменить флажками.
Остальные столбцы сопоставляются по порядку, а раскрытый блок соответствий
показывает примеры содержимого. Проверьте или измените соответствие перед
добавлением, особенно если набор или порядок столбцов отличается. При исключении
столбца позиции остальных не сдвигаются. Неизвестный статус можно обозначить
флажком и сопоставить вручную. Предпросмотр и отмена добавления работают как для
полного чек-листа. При обычном импорте с заголовками сохраняется сопоставление
по названиям.

Фразы в ячейках, в том числе «не проверено напрямую», «Окружение: DEV» и
«Статус: OK», сохраняются как содержимое и не меняют реквизиты отчёта.

Проверки: `node --test tests/headerless-import.test.js`; полный браузерный сценарий —
`node tests/headerless-import.browser.cjs` с Playwright (или путём к пакету в
`QA_REPORT_PLAYWRIGHT`). Используются временная база и тестовые данные; внешние
запросы блокируются.

После разбора источника выберите назначение:

- «Добавить новые разделы»: в конец, начало или после выбранного раздела.
  Отмеченные пункты сохраняют разделы и свои столбцы. Совпадающие названия
  не объединяются: окно предупреждает, что будут добавлены отдельные разделы.
- «Добавить в существующий раздел»: пункты всех выбранных разделов источника
  добавляются в конец выбранного раздела в исходном порядке. Столбцы сопоставляются
  по названию без учёта регистра и лишних пробелов. Несопоставленные столбцы
  добавляются; прежние строки получают в них пустые ячейки. В раскрываемом блоке
  «Настроить соответствие столбцов» можно выбрать другое соответствие или новый
  столбец. Два столбца одного раздела источника нельзя направить в один столбец.
  Если включена сортировка по статусу, она сохраняется и учитывается в предпросмотре.
- «Заменить чек-лист»: прежний сценарий полной замены с подтверждением для
  заполненного отчёта. В пустом стандартном чек-листе этот режим выбран сразу;
  в заполненном по умолчанию предлагается добавление новых разделов.

При добавлении сохраняются существующие пункты, результаты, вложения, ссылка
на задачу, окружение, итог и вводный текст. Описание и реквизиты источника
не добавляются. Настройки статусов, очистки данных и вложений действуют только
на импортируемые пункты. Режим нумерации текущего отчёта сохраняется: автоматические
номера рассчитываются по итоговому положению, ручные номера новых пунктов можно
сохранить из источника или оставить пустыми. Старые ручные номера не меняются.

Предпросмотр показывает только добавляемые пункты с итоговыми столбцами и номерами.
После импорта новые строки подсвечиваются; кнопка «Отменить» в уведомлении либо
хедере отменяет весь импорт вместе с новыми столбцами одним действием. «Повторить»
возвращает его. Если чек-лист изменился во время настройки, потребуется проверить
обновлённый предпросмотр перед применением.


После чтения комментария или разметки откроется «Настроить импорт». Вкладка
«Пункты» позволяет сопоставить исходные статусы, отобрать нужные статусы,
разделы и строки. Незнакомые и неоднозначные статусы требуют выбора соответствия;
исходные названия остаются доступны до завершения импорта. Фильтр применяется
к сопоставленным исходным статусам, до сброса для нового тестирования.

Во вкладке «Столбцы и данные» для каждого столбца можно сохранить содержимое,
оставить пустой столбец или исключить его. Можно задать исключения для отдельных
строк. При замене чек-листа можно убрать описание источника и сохранить исходные
номера в ручном режиме; отключение опции пересчитывает номера. В каждом выбранном разделе должен остаться
хотя бы один содержательный столбец. Пустые после отбора разделы не переносятся.

Настройка «Для повторного тестирования» очищает распознанный столбец фактического
результата (включая ФР, Факт, Actual Result), сбрасывает статусы пунктов и общий
статус в «НЕ ПРОВЕРЕНО» при замене чек-листа. При добавлении меняются только
новые пункты, а режим нумерации и общий итог текущего отчёта сохраняются. Если столбец не распознан,
окно предлагает выбрать его вручную. Фильтры и ручной выбор пунктов сохраняются.

Во вкладке «Вложения» можно исключить изображения целиком, включая ссылки и
обёртки из вставленной разметки, сохранив текст ячеек. Остальные вложения можно
оставить ссылками, исключить или, при импорте комментария, скачать в браузер.
Исключения задаются для раздела, столбца, строки и файла: файл имеет высший
приоритет, затем строка, столбец и раздел. Выключение изображений действует на
все уровни. Из исключённых пунктов и очищенных ячеек файлы не скачиваются.
Одинаковый файл скачивается один раз, но перенос в каждую ячейку настраивается
отдельно. Смена общей настройки вложений сбрасывает частные исключения.

Предпросмотр показывает итоговый текст, номера и статусы без загрузки изображений.
Все настройки применяются к копии исходных данных. Перед импортом сохраняется
текущий отчёт; заполненные данные заменяются только после подтверждения.

Проверки настройки импорта: `node --test tests/import-options.test.js`; браузерные проверки исключения и скачивания файлов — `tests/import-attachments.browser.html` на локальном сервере приложения. Они используют только тестовые данные и не обращаются к Jira.

Проверки частичного импорта: `node --test tests/partial-import.test.js tests/report-editing.test.js`.

### Поля отчёта через API и сохранение больших импортов

Подключение в AI-режиме действует 5 часов с момента включения приёма.
В окне приёма постоянно видны оставшееся время и время отключения, включая
ожидание следующих пакетов. Можно включить приём отдельно в трёх отчётах
и переключаться между ними в одной открытой вкладке. Для каждого отчёта
используются собственный промпт, временный ключ и кнопка «Остановить».
Другие активные подключения видны в том же окне. Перезагрузка вкладки
восстанавливает подключения без продления срока; закрытая вкладка не принимает
результаты. Сохранение фонового отчёта проверяет, что его копия в IndexedDB
не изменилась и не была удалена во время обработки пакета.

Временный API приёма от ИИ поддерживает ссылку или ключ задачи, окружение
(в том числе адрес стенда), общий «Итог» и вводный текст. Поля можно передать
отдельно или вместе с результатами; проверка hash защищает от перезаписи
параллельных правок. Контракт и примеры — в [локальном импорте](docs/local-import.md).

Если большой отчёт с вложениями не помещается в localStorage, индикатор
дожидается сохранения в IndexedDB. «Ошибка сохранения» появляется только при
неудаче обоих локальных способов сохранения; несохранённые изменения остаются
помеченными. Запоздавший результат предыдущего сохранения не меняет статус
новых правок или другого отчёта.

## Полная копия репорта (.report)

В меню «Экспорт» доступны «Сохранить копию (.report)», «Копировать как HTML»,
«Копировать для Jira» и «Скачать Excel (.xlsx)».
Перед копированием HTML открывается окно выбора разделов и статусов пунктов.
По умолчанию отмечено всё. Фильтры применяются вместе; пустые разделы не копируются,
а номера пунктов, описание и реквизиты остаются исходными. После нажатия
«Копировать HTML» окно остаётся открытым, кнопка показывает «Скопировано в буфер обмена».
Можно изменить выбор и скопировать снова; закрыть окно крестиком или Escape.
При копировании как HTML столбцы получают достаточную ширину для заголовков и
обычных слов. Текст переносится по словам; если редактор сужает столбец сильнее,
длинное слово переносится без дефиса и не перекрывает соседнюю ячейку.
Длинные URL переносятся внутри своих ячеек и не перекрывают соседние столбцы.
После скачивания появляется короткое сообщение «Копия отчёта скачана».
Флажок «Больше не показывать это сообщение» запоминается при закрытии окна
в текущем браузере, в том числе после перезагрузки. Подготовка файла и ошибки
экспорта остаются видимыми.
Для открытия выберите «Импорт» → «Файл .report»: перетащите один файл в область
загрузки или выберите его на компьютере, затем нажмите «Открыть отчёт».
До нажатия этой кнопки текущий отчёт не меняется. Выбранный файл можно убрать
и заменить другим; ошибки выбора, чтения и проверки показываются в том же окне.
Компактное окно импорта сохраняет размер и положение заголовка, вкладок и
кнопок при переключении способов импорта. Разметка прокручивается внутри поля;
карточка выбранного .report показывает имя и размер, позволяет заменить или
убрать файл. Без файла «Открыть отчёт» недоступна. Светлая и тёмная темы
используют одинаковые размеры окна.
Копия содержит текущее описание, разделы, колонки, результаты, статусы, форматирование,
нумерацию и все вложения. Изменения в открытом редакторе включаются сразу.
Файл можно хранить вне браузера или передать другому пользователю QA Report.
Это снимок на момент скачивания: после следующих правок скачайте новую копию.

Локальные вложения включаются без сети. Ссылочные вложения Jira и хранилища
скачиваются через существующий доступ; для Jira необходимо активное подключение.
Если хотя бы одно вложение недоступно, копия не скачивается: окно показывает причины.
Обычные гиперссылки остаются ссылками и не архивируют содержимое сайтов.
Лимит одной копии — 250 МиБ и 1000 уникальных вложений.

Открытие проверяет формат и целостность документа и каждого вложения. До замены
редактора предыдущий отчёт и новая копия записываются одной транзакцией в локальную
историю. При нехватке места текущий отчёт остаётся открытым. Импорт создаёт новые
идентификаторы, не перезаписывает оригинал и сам по себе не отправляет копию в облако.
Дальнейшее сохранение следует существующей настройке облачной истории браузера.
Настройки приложения, сессии, пароли и токены не включаются. Файл содержит данные
отчёта и вложения без шифрования. История отмены и другие отчёты в копию не входят.

Формат v1 — ZIP без сжатия с manifest.json, report.json и бинарными вложениями,
объединёнными по SHA-256. Проверяются контрольные суммы ZIP, SHA-256 документа и
вложений, версия формата и структура отчёта; HTML очищается перед отображением.
Открывайте файл через QA Report; двойной щелчок не запускает отдельный просмотрщик.

Браузерная проверка окна импорта: `node tests/report-import.browser.cjs`
(нужен Playwright; путь к установленному пакету можно указать в
`QA_REPORT_PLAYWRIGHT`). Проверка запускает отдельный локальный сервер и тестовую
базу, проверяет выбор и перетаскивание, ошибки, восстановление с вложениями,
историю, остальные источники импорта, экспорт и размеры окна. Внешние сервисы
не вызываются; снимки можно сохранить через `QA_REPORT_SCREENSHOTS`.

### Навигация в хедере

Меню **Report** переключает между Report и [QA Capture](https://qa-capture.mlbrg.ru/); Capture открывается в новой вкладке.

Кнопка **Импорт** рядом с «Новый» открывает импорт чек-листа, комментария Jira или файла отчёта.
В меню **Экспорт** собраны отправка и копирование для Jira, сохранение `.report`, Excel и HTML.
Тема выбирается в **Настройки → Приложение → Внешний вид**, подключение Jira — в **Настройки → Интеграции → Jira**.
Индикатор рядом с Report показывает сохранение; наведите на него курсор или выделите клавишей Tab для подробностей.
Кнопка AI использует нейтральную точку при выключенном приёме и зелёную — при включённом.

### Копирование и перенос в раздел

В режиме выделения откройте «Копировать или перенести» и выберите действие.
По умолчанию выбрано «Копировать»: исходные строки остаются на месте и сохраняют
выделение. «Перенести» удаляет их из исходных разделов; уже находящиеся в целевом
разделе строки остаются на месте. При копировании можно выбрать и исходный раздел,
чтобы добавить в него дубликаты выбранных строк.

Найдите раздел по названию или нажмите «Создать новый раздел». Новый раздел
добавляется в конец списка после подтверждения. Можно раскрыть и свернуть форму,
не теряя введённое название. Отмена сохраняет данные и выделение.
Обе операции сохраняют статусы, форматирование, вложения и ручные номера пунктов.
Строки добавляются в конец в порядке исходных разделов и строк. Столбцы
сопоставляются по названию; недостающие поля добавляются в целевой раздел.
Копирование доступно и при сортировке по статусу. Для переноса сначала верните
исходный порядок в выбранных разделах и разделе назначения. Обе операции
отменяются кнопкой отмены; повтор возвращает результат.

Проверки: `node --test tests/checklist-selection.test.js tests/checklist-table.test.js`;
браузерные сценарии — `node tests/selection-transfer.browser.cjs` с Playwright
(или путём в `QA_REPORT_PLAYWRIGHT`). Проверяются копирование, перенос, создание
раздела, поиск, отмена, повтор, сохранение после перезагрузки и узкий экран.
Используются временная база и тестовые данные; внешние запросы блокируются.

### Копирование выбранных пунктов

В режиме выделения кнопка «Копировать в новый чек-лист» создаёт отдельный
чек-лист с новой ссылкой из выбранных пунктов и разделов. Сохраняются колонки,
статусы, форматирование, вложения и реквизиты. В окне копирования выберите структуру и флажки сохранения номеров разделов и пунктов.
Сохранённые номера редактируются вручную. При снятом флажке номера пунктов
пересчитываются в прежнем автоматическом режиме; для ручного режима — с 1 в каждом разделе.
«Отмена» не создаёт копию.
Крестик в правом верхнем углу панели завершает режим выделения. Оба чек-листа
сохраняются в истории; исходные пункты остаются на месте. После копирования окно
показывает количество скопированных пунктов и предлагает «Открыть новый»
или «Остаться в текущем».

Проверки копирования: `node --test tests/checklist-selection.test.js`; браузерные
сценарии — `node tests/selection-copy.browser.cjs` и `node tests/html-copy-scope.browser.cjs`
с Playwright (или путём в `QA_REPORT_PLAYWRIGHT`). Проверяются оба варианта нумерации,
отмена, сохранение истории, фильтры HTML, буфер обмена и панель на узком экране.
Используются временная база и тестовые данные, внешние запросы блокируются.

### Номера разделов и структура копии

В «Настройки → Чек-лист» нумерация разделов настраивается отдельно от пунктов.
«По порядку» пересчитывает разделы при перестановке и удалении. «Вручную — сохранить
номера» фиксирует текущие номера; их можно изменить прямо перед названием раздела,
например, на 4, 8 и 12. Для нового раздела в ручном режиме номер задаётся вручную.
При нумерации пунктов «По номеру раздела и пункта» используется фактический номер
раздела, поэтому раздел 8 содержит пункты 8.1, 8.2 и далее. Ручные номера пунктов
меняются независимо. Перенос пунктов в существующий раздел не меняет его номер.

«Копировать в новый чек-лист» открывает выбор структуры: сохранить разделы с их
столбцами и выбранными пунктами либо объединить пункты в один новый раздел.
В окне копирования выбор одного варианта структуры показан карточками с подсветкой.
Отдельный блок «Нумерация» содержит независимые флажки сохранения номеров
пунктов и разделов. Кнопка «Создать копию» применяет выбранные настройки. При объединении столбцы
сопоставляются по названию; различающиеся поля и вложения сохраняются. Новый общий
раздел получает собственный номер 1. Отмена не создаёт копию и не меняет исходный лист.

Номера разделов сохраняются в истории, файлах .report, HTML, Excel и публикации
в Jira. При импорте числовых заголовков вроде «8. Раздел» можно отдельно сохранить
номера разделов. Добавление целых разделов учитывает этот выбор; добавление пунктов
в существующий раздел сохраняет его номер. Старые отчёты без настройки разделов
открываются с прежней нумерацией по порядку.

Проверки номеров разделов: `node --test tests/section-numbering.test.js` и
`node tests/section-numbering.browser.cjs` с Playwright. Проверяются независимые
режимы и флажки копирования, объединение пунктов, редактирование, удаление,
перестановка разделов, повторное открытие, .report, экспорт и импорт.
Браузерная проверка использует временную базу, тестовые данные и блокирует внешние запросы.

## Диктовка в редакторе

Поставьте курсор в текстовую ячейку, вводный текст или название раздела и нажмите
микрофон справа от скрепки. Во время
записи видны REC и таймер; повторное нажатие завершает запись, затем отображается
распознавание и, если оно включено, приведение текста в порядок. Крестик или Esc
отменяет текущий фрагмент. Запись ограничена тремя минутами.

Используются настройки Connect → ИИ → «Распознавание речи». «Без обработки»
оставляет исходную расшифровку; «Исправить ошибки» сохраняет формулировки;
«Улучшить формулировку» убирает повторы и слова-паразиты. Обработку выполняет
подключение ИИ по умолчанию. При включённой обработке расшифровка отправляется
этому подключению даже при локальном распознавании голоса.

Место вставки сохраняется на время записи и обработки. Если оно не выбрано,
удалено, изменено или открыт другой отчёт, текст копируется в буфер обмена.
Если браузер запрещает копирование, текст остаётся на экране с кнопкой
«Скопировать текст». Новый фрагмент не заменяет этот результат, пока он не
скопирован или явно закрыт. Вставку можно отменить одним действием отмены.
При ошибке обработки исходная расшифровка сохраняется и выводится пояснение.

Браузерная проверка: `node tests/dictation.browser.cjs` с настроенным
`QA_REPORT_PLAYWRIGHT`. Она использует синтетическое аудио и ответы Connect.

Подключение Connect доступно в Настройки → QA Report Connect. Код создаётся
только в корпоративной сессии с CSRF-проверкой, действует 10 минут и используется
один раз. Connect получает отдельный ключ только для очереди распознавания и
обработки текста. Этот ключ не даёт доступа к отчётам, Jira или другим API.
Владельца диктовки определяет проверенная сессия с текущим пространством;
чужие подключения и задания недоступны. Проверки origin, лимиты запросов,
security headers и аудит сохраняются. Аудио и исходный текст удаляются из
завершённых заданий; результаты и незавершённые задания очищаются по истечении
пяти минут. Сервер не получает ключи ИИ-провайдеров. Для работы нужно отдельно
разрешённое в корпоративной среде приложение Connect и доступ к выбранной модели.

Для диктовки `Permissions-Policy` разрешает микрофон только своему origin
(`microphone=(self)`). Камера, геолокация, платежи и USB остаются запрещены.
Браузер отдельно запрашивает согласие на доступ к микрофону.

### Проверка связи отчёта с Jira

`node --test tests/jira-publication.test.js` проверяет владельца, изменение
комментария, сохранение видимости, конфликт, повтор после неопределённого
результата и очистку связи у копии. `node tests/jira-publication.browser.cjs`
проверяет публикацию, обновление, создание нового комментария, локальное
сохранение, историю, копию отчёта, темы и узкий экран, доступность меню
публикации и отсутствие перекрытия верхней панели и окна обновления.
Сценарий также проверяет сброс связи с удалённым комментарием, сохранение связи
при ошибках доступа и временных сбоях, облачное сохранение, отмену и новую публикацию.
Для браузера нужен Playwright; путь можно указать в `QA_REPORT_PLAYWRIGHT`, снимки — в
`QA_REPORT_SCREENSHOTS`. Используются временная БД и синтетические ответы;
реальные комментарии Jira не изменяются.


### Мастер создания баг-репорта

«Bug Report» в меню Report и «Завести баг-репорт» в меню строки открывают
мастер из трёх шагов: «Место создания», «Подготовка», «Баг-репорт».
Основные окна имеют одинаковую ширину и высоту; заголовок и действия остаются
видимыми, содержимое прокручивается. Поддерживаются светлая, тёмная и графитовая
темы. Сначала выберите «Самостоятельная задача» или «Подзадача». До выбора проект,
родительская задача и тип задачи недоступны; запросы типов и полей не запускаются.
После выбора варианта, проекта или родительской задачи загружается соответствующая
форма. Незавершённое создание восстанавливает сохранённый вариант.
Пока форма загружается, «Продолжить»
неактивна и показана приглушённым цветом; после загрузки выбранного типа
кнопка становится доступной.

На шаге «Подготовка» опишите проблему в одном поле. При создании бага из
пункта чек-листа его контекст передаётся автоматически: поле «Уточнения для ИИ»
необязательно, о чём сообщает подсказка над ним. Добавляйте файлы кнопкой,
перетаскиванием или вставкой; диктовка дополняет этот же текст. Выберите
подключение ИИ и при необходимости измените промпт кнопкой «Настроить промпт».
Панель вложений и диктовки закрепляется над навигацией при растягивании поля,
а подсказка о способе распознавания открывается по значку «i».
Текст и файлы сохраняются. Во время генерации показан индикатор ожидания;
после ответа ИИ открывается черновик, который можно редактировать
сразу в просторных полях. Вкладка «Визуально» показывает форматирование сразу;
«Разметка» открывает тот же текст в Jira Wiki. Панель меняет выделенный текст
на жирный, курсив, подчёркивание, список, ссылку или код. Command+Z / Ctrl+Z
отменяют ввод, форматирование и вставки в активном поле; Command+Shift+Z /
Ctrl+Y повторяют отменённое. Отмена в окне бага не меняет чек-лист.
Обязательные поля отмечены
звёздочкой по метаданным Jira. Дополнительные параметры и соответствие разделов
полям Jira раскрываются отдельно. Если отдельного поля для шагов или результатов
нет, эти разделы редактируются отдельно и добавляются в описание при создании.

Разделитель в черновике перетаскивается мышью и управляется стрелками клавиатуры;
выбранная пропорция сохраняется в браузере. Двойной щелчок сбрасывает ширины.
На узком экране колонки располагаются друг под другом.
Выбранные компоненты, версии и метки показаны внутри полей рядом с поиском;
крестик убирает отдельное значение, стрелка открывает доступные варианты.
Возврат назад сохраняет параметры и черновик. После возврата к подготовке
кнопка «Перейти к черновику» открывает прежние правки без перегенерации.
При отсутствии подключения ИИ можно перейти к ручному заполнению.
Успешное создание открывает компактное окно с одной ссылкой по ключу задачи,
темой и кнопкой «Создать ещё один». Заголовок нейтрален к системе задач.
Счётчик «Вложения: N из M загружено» показывает маленький индикатор во время
отправки и галочку после загрузки и добавления ссылок. Повторные сообщения и
кнопки закрытия убраны; закрытие доступно крестиком. Незавершённая загрузка
вложений сохраняет
возможность повтора без создания дубликата задачи.

Проверка интерфейса: `node tests/bug-wizard.browser.cjs` с Playwright.
Выбор варианта и итоговый экран: `node tests/bug-success.browser.cjs`.
Стенд в `tests/fixtures/bug-wizard-preview.cjs` использует исключительно тестовые
ответы Jira и ИИ и не обращается к внешним сервисам.

Корпоративные операции мастера проходят через существующие сессию, CSRF,
allowlist Jira и пользовательское OAuth-подключение. Jira не вызывается через
Connect. Создание повторно проверяет метаданные полей и сохраняет результат
операции отдельно для пользователя и подключения; повтор с тем же идентификатором
не создаёт новую задачу. Connect выполняет только задания речи и ИИ в существующей
очереди своего владельца, с очисткой материалов после завершения. Подготовка
черновика требует подключения модели в Connect. Промпт хранится в браузере.
Проверки защиты: `node --test tests/bug-report-server.test.js tests/connect-dictation.test.js`.

Вложения из подготовки доступны справа в черновике и по кнопке скрепки
на панели «Описание». Вставка сохраняет выбранную позицию курсора.
Здесь же можно загрузить новый файл; изображение из буфера обмена или
перетаскивания отображается локальным превью в визуальном редакторе.
Перетащите файл в нужное
место описания или нажмите «В описание»; новый файл можно бросить в описание
или вставить из буфера. Остальные поля принимают только текст. При снятии
выбора файла его вставки удаляются; после создания задачи вставки заменяются
ссылками на загруженные файлы (изображения в Jira Server/Data Center — превью).
Невставленные файлы добавляются в конец описания.

Закрытие мастера — крестиком; во время создания задачи закрытие блокируется.

В светлой теме кнопка публикации рядом с заголовком отчёта имеет светлый полупрозрачный фон, как остальные панели.


На подготовке нет повторяющихся пояснений; рядом с «Настроить промпт» указано,
что в промпте можно задавать значения полей и условия их автоматического
предзаполнения. Заголовок мастера не зависит от выбранной системы задач.

Скрепка в редакторе «Описание» сразу открывает выбор файла, если вложений ещё
нет. Иначе она предлагает новые файлы и вложения текущего чек-листа. Один файл
можно вставлять несколько раз без повторной загрузки; исходное имя сохраняется.
При совпадении имён разных файлов при отправке добавляется числовой суффикс.
Добавленные поддерживаемые файлы автоматически выбираются для анализа ИИ;
их можно исключить на подготовке. При пересборке вставки сохраняются в описании.
Одна кнопка «Блок кода» оборачивает выделенный текст: визуальный режим показывает
оформление, разметка передаётся в Jira Wiki, а Jira Cloud получает соответствующие
текстовые блоки. Буквальные символы разметки в визуальном режиме экранируются.

В редактор перенесены стили заголовков, зачёркивание и палитра чек-листа.
При вставке скопированного HTML сохраняются текст, изображения и файлы с
исходными именами. Вкладка «Разметка» показывает файлы как `[^имя]`, изображения
как `!имя|thumbnail!`; повторная вставка использует то же вложение.
При отправке временные места вставки привязываются к подтверждённым файлам
созданной задачи: Jira Server/DC получает родные ссылки и миниатюры, Jira Cloud —
ссылки на загруженные файлы. Совместимость загрузки с Connect 0.6.17 сохранена.

Заголовки, зачёркивание и цвета поддерживаются при отправке в Jira Cloud
начиная с Connect 0.6.18. Подписанный пакет включён в публичный каталог
обновлений; проверяются подпись, размер, SHA-256 и совместимость установленного
приложения. Для этого обновления отдельный установщик не нужен.

Проверки приёма ИИ: `node --test tests/local-import.test.js tests/local-import-client.test.js`.
Браузерная проверка трёх отчётов, таймеров, остановки, перезагрузки и конфликтов
сохранения: `node tests/local-import.browser.cjs`. Для установленного отдельно
Playwright задайте `QA_REPORT_PLAYWRIGHT`; для снимков окна — `QA_REPORT_SCREENSHOTS`.

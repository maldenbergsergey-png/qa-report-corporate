# Закрытая админка: MVP

Админка и сбор посещений выключены, пока не создан файл конфигурации.
Адрес по умолчанию — `/owner/`; доступ к статистике проверяется сервером по
отдельной сессии. Читаемый адрес не заменяет проверку пароля.
Обычный вход пользователя не даёт прав администратора. В каждой установке
создаются собственные конфигурация и база; объединения данных между версиями нет.

## Настройка без Docker

Из каталога приложения в интерактивном терминале:

```bash
npm run admin:setup
```

Введите логин и уникальный пароль из менеджера паролей (16–256 символов).
Ввод пароля скрыт. Команда сохранит только соль и scrypt-хеш (N=2^17, r=8, p=1),
постоянный адрес `/owner/` и независимый ключ cookie посетителей в
`secrets/admin/admin.json` с правами `0600`. Этот каталог исключён из Git.
Адрес будет выведен в терминал. Другой читаемый адрес можно задать параметром
`--path /control-room`; существующий случайный адрес можно заменить командой
`npm run admin:setup -- --path /owner` без смены пароля. Не передавайте пароль
через аргументы, переменные окружения или чат.

В production требуется `QA_REPORT_PUBLIC_URL=https://<ваш-домен>` и HTTPS.
При TLS termination включите `QA_REPORT_TRUST_PROXY=true` только за доверенным
proxy, который перезаписывает `X-Forwarded-For` и `X-Forwarded-Proto`;
прямой доступ к порту Node из интернета должен быть закрыт.
Админка проверяет HTTPS по TLS-сокету либо по `X-Forwarded-Proto: https`
доверенного proxy. Заголовки клиента без этого флага не принимаются.
Для локальной проверки допустим `NODE_ENV=development` с `HOST=127.0.0.1`.

Перезапустите сервер. Откройте выведенный путь на домене этой установки.
`QA_ADMIN_CONFIG_FILE` позволяет указать другой файл; `QA_ADMIN_TIMEZONE`
задаёт часовой пояс суток (по умолчанию `Europe/Moscow`).

## Docker Compose

Обновлённый `compose.yaml` подключает отдельный volume `admin_config` только
для чтения в приложении. Служебный контейнер с профилем `admin` записывает
конфигурацию от пользователя `node`, без доступа к сети, пользовательской базе
и другим секретам:

```bash
docker compose --profile admin build
docker compose run --rm --no-deps admin-setup
docker compose up -d --build qa-report
```

Перед включением задайте HTTPS URL и доверие к proxy в конфигурации окружения,
как описано выше. Логин и пароль не имеют значений по умолчанию.
Сохраните volume `admin_config` при пересоздании контейнера.

Если Compose хранится вне checkout, точечно перенесите в него новый volume,
переменные `QA_ADMIN_*`, HTTPS URL, настройку proxy и сервис `admin-setup` из
подходящего шаблона. Обычное обновление исходников не меняет внешний Compose.
После обновления образа выполните команды настройки из каталога этого Compose.

Смена пароля:

```bash
npm run admin:setup -- --rotate-password
# или
docker compose run --rm --no-deps admin-setup node scripts/setup-admin.cjs --rotate-password
```

Перезапустите приложение после смены пароля: все админские сессии будут отозваны.
Адрес и ключ идентификаторов посетителей сохраняются. Удаление конфигурации и
перезапуск отключают вход и сбор; существующая статистика остаётся в базе.
Для полного удаления остановите приложение и удалите только служебный каталог
`admin` рядом с `REPORTS_DB_PATH`, не базу отчётов. Резервные копии удаляются отдельно.

## Автоматическая первоначальная настройка

Чтобы оператор мог выполнить настройку целиком, без ввода пароля в чате:

```bash
node scripts/setup-admin.cjs --generate --path /owner --access-file ./secrets/admin-access.json
```

Команда создаёт отдельного администратора `owner` со случайным паролем из
32 случайных байт. Серверная конфигурация содержит только хеш. Пароль для
передачи владельцу сохраняется в отдельном локальном файле с правами `0600`,
который не попадает в Git. Заберите данные в менеджер паролей, затем удалите
файл выдачи. Команда не печатает пароль в stdout или stderr. Повторный запуск
сохраняет существующий пароль и ключ посетителей; `--path` меняет только адрес.
Для явной смены пароля нужен `--rotate-password` и новый файл выдачи.

## Сохранность при обновлении

Конфигурация администратора находится в постоянном томе `admin_config`,
статистика — в `reports_data`. Пересборка образа, пересоздание контейнера и
Git pull не меняют эти данные. Рабочий Compose хранит подключения томов;
нельзя удалять тома при обычном обновлении. Внешний Compose обновляется
точечно: имя проекта и существующие тома сохраняются. Автообновление меняет
только тег образа и не копирует шаблон Compose поверх рабочего файла.
При изменении адреса пароль и ключ посетителей сохраняются.

## Доступ и данные

- Сессия администратора живёт 8 часов, хранится на сервере в памяти по хешу
  случайного токена и теряется при перезапуске. Cookie: `HttpOnly`,
  `SameSite=Strict`, `Secure` в production, путь ограничен адресом админки.
- Вход ограничен 10 попытками за 15 минут на IP и 100 на установку;
  одновременно выполняется не более одной проверки scrypt. Изменяющие запросы
  требуют точного Origin и специального заголовка, выход — ещё и CSRF-токена.
- Страницы и API админки имеют `no-store`, `noindex`, запрет фреймов и строгую CSP.
  Служебные исходники, скрытые файлы, секреты и каталог базы не раздаются статикой.
  PWA кеширует только общий скрипт сбора, не админку и не её ответы.
- Cookie посетителя содержит случайный ID с HMAC-подписью и действует до года.
  Это идентификатор браузера, а не подтверждённой личности. Очистка cookie,
  приватное окно и разные устройства дают разные ID; одинаковые IP не объединяются.
- Сигнал отправляется при открытии видимого редактора, возвращении к нему и
  каждые 5 минут активности. В теле сигнала передаётся только режим PWA/браузер.
  IP берётся из соединения (из заголовка — только при доверии к proxy), браузер,
  ОС и тип устройства приблизительно определяются по User-Agent. Сырой User-Agent,
  URL отчёта, содержимое чек-листов, пароли и Jira-токены не записываются.
  Для подтверждённых входов сохраняются ID аккаунта, имя и почта, если доступны;
  они видны только авторизованному администратору.
- Новый визит: первый сигнал в режиме, 30 минут с последнего сигнала в нём
  или новый календарный день. Несколько вкладок с общей cookie не удваивают визит.
  PWA и браузер имеют отдельные визиты и могут иметь общий ID; их аудитории пересекаются.
- Аккаунт связывается со случайным ID браузера только по проверенной сервером
  сессии. Аккаунт из тела запроса, IP и произвольных заголовков не принимается.
  Связь сохраняется после выхода и смены IP; несколько аккаунтов одного браузера
  показываются отдельно. Очистка cookie создаёт новый браузер, который можно
  связать с аккаунтом только после следующего подтверждённого входа.
- Работа офлайн не накапливает сигналы. Статистика начинается после настройки;
  прошлые посещения восстановить нельзя. Подделанные клиентом сигналы и блокировщики
  могут влиять на цифры; это оценка использования, не биллинг и не аудит личности.
- SQLite `admin/usage.sqlite` рядом с базой отчётов хранит дневные агрегаты за
  последние 90 календарных дней. Пока функция включена, очистка выполняется при запросах и каждый час.
  Связи аккаунтов хранятся 90 календарных дней с последнего подтверждённого
  входа независимо от более поздних анонимных посещений; удаляются автоматически.
  Прежняя статистика сохраняется, новая таблица связей создаётся при открытии базы.
  Поиск по ID аккаунта, имени или почте находит все связанные браузеры,
  в том числе PWA. Счётчик посетителей по-прежнему считает браузеры.
  Доступ к файлу `0600`, к новому каталогу `0700`; резервные копии содержат IP и аккаунты
  и должны храниться с такими же ограничениями и собственным сроком удаления.

В корпоративной версии используется только `request.user.email`, полученный
существующей проверкой корпоративной сессии. Сигналы без неё по-прежнему
отклоняются до сбора статистики. Схема входа, CSRF и права не меняются.

Проверки: `npm run check`, `npm test`; отдельно
`node --test tests/admin.test.js` и `node tests/admin.browser.cjs` (нужен Playwright).

## Личные облачные отчёты

«Разрешить сохранение личных отчётов в облаке» включает создание и обновление
личных копий независимо от публикаций для коллег. По умолчанию флаг выключен.
При выключении владелец может открыть и удалить прежнюю копию. Текст находится
в базе приложения, файлы — в отдельном закрытом разделе S3. Администратор
управляет разрешением, но не получает доступ к чужим личным отчётам.
